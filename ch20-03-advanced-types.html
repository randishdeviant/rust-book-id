The Rust Programming Language

Tipe Lanjutan

Sistem tipe Rust memiliki beberapa fitur yang sejauh ini kami sebutkan tapi belum dibahas. Kami akan memulai dengan membahas newtype secara umum saat kami memeriksa mengapa mereka berguna sebagai tipe. Lalu, kami akan lanjut ke type aliases, fitur yang mirip dengan newtype tapi dengan semantik sedikit berbeda. Kami juga akan membahas tipe ! dan dynamically sized types.

Keamanan Tipe dan Abstraksi dengan Pola Newtype

Bagian ini mengasumsikan Anda telah membaca bagian sebelumnya “Mengimplementasikan Trait Eksternal dengan Pola Newtype”. Pola newtype juga berguna untuk tugas di luar yang telah kami bahas sejauh ini, termasuk menegakkan secara statis bahwa nilai tidak pernah bercampur dan menunjukan satuan dari sebuah nilai. Anda melihat contoh penggunaan newtype untuk menunjukan satuan di Listing 20-16: Ingat bahwa struct Millimeters dan Meters meng-wrap nilai u32 dalam newtype. Jika kita menulis fungsi dengan parameter bertipe Millimeters, kita tidak akan bisa mengompilasi program yang tidak sengaja mencoba memanggil fungsi itu dengan nilai bertipe Meters atau u32 biasa.

Kita juga bisa menggunakan pola newtype untuk mengabstraksi detail implementasi sebuah tipe: Tipe baru bisa mengekspos API publik yang berbeda dari API tipe dalam privat.

Newtype juga bisa menyembunyikan implementasi internal. Misalnya, kita bisa menyediakan tipe People untuk wrap HashMap<i32, String> yang menyimpan ID orang yang terkait dengan nama mereka. Kode yang menggunakan People hanya akan berinteraksi dengan API publik yang kami sediakan, seperti metode untuk menambah string nama ke koleksi People; kode itu tidak perlu tahu bahwa kami menetapkan ID i32 ke nama secara internal. Pola newtype adalah cara ringan untuk mencapai enkapsulasi guna menyembunyikan detail implementasi, yang kami bahas di bagian “Enkapsulasi yang Menyembunyikan Detail Implementasi” di Bab 18.

Sinonim Tipe dan Type Aliases

Rust menyediakan kemampuan untuk mendeklarasikan type alias untuk memberi nama lain pada tipe existing. Untuk ini kita menggunakan kata kunci type. Misalnya, kita bisa membuat alias Kilometers ke i32 seperti ini:

fn main() {
    type Kilometers = i32;

    let x: i32 = 5;
    let y: Kilometers = 5;

    println!("x + y = {}", x + y);
}

Sekarang alias Kilometers adalah sinonim untuk i32; tidak seperti tipe Millimeters dan Meters yang kami buat di Listing 20-16, Kilometers bukan tipe baru yang terpisah. Nilai yang bertipe Kilometers akan diperlakukan sama seperti nilai bertipe i32:

fn main() {
    type Kilometers = i32;

    let x: i32 = 5;
    let y: Kilometers = 5;

    println!("x + y = {}", x + y);
}

Karena Kilometers dan i32 adalah tipe yang sama, kita bisa menambahkan nilai kedua tipe tersebut dan bisa meneruskan nilai Kilometers ke fungsi yang menerima parameter i32. Akan tetapi, menggunakan metode ini, kita tidak mendapat manfaat pemeriksaan tipe yang kita dapatkan dari pola newtype yang dibahas sebelumnya. Dengan kata lain, jika kita mencampurkan nilai Kilometers dan i32 di suatu tempat, compiler tidak akan memberi error.

Kasus penggunaan utama untuk sinonim tipe adalah mengurangi pengulangan. Misalnya, kita mungkin memiliki tipe panjang seperti ini:

Box<dyn Fn() + Send + 'static>

Menulis tipe panjang ini di tanda tangan fungsi dan sebagai anotasi tipe di seluruh kode bisa melelahkan dan rawan error. Bayangkan memiliki proyek penuh kode seperti di Listing 20-25.

Type alias membuat kode ini lebih mudah dikelola dengan mengurangi pengulangan. Di Listing 20-26, kami memperkenalkan alias bernama Thunk untuk tipe verbose dan bisa mengganti semua penggunaan tipe dengan alias pendek Thunk.

Kode ini jauh lebih mudah dibaca dan ditulis! Memilih nama yang bermakna untuk type alias bisa membantu mengomunikasikan niat Anda sekaligus (thunk adalah kata untuk kode yang dievaluasi nanti, jadi nama ini cocok untuk closure yang disimpan).

Type aliases juga sering digunakan dengan tipe Result<T, E> untuk mengurangi pengulangan. Pertimbangkan modul std::io di pustaka standar. Operasi I/O sering mengembalikan Result<T, E> untuk menangani situasi saat operasi gagal bekerja. Pustaka ini punya struct std::io::Error yang mewakili semua error I/O yang mungkin. Banyak fungsi di std::io akan mengembalikan Result<T, E> di mana E adalah std::io::Error, seperti fungsi-fungsi ini di trait Write:

use std::fmt;
use std::io::Error;

pub trait Write {
    fn write(&mut self, buf: &[u8]) -> Result<usize, Error>;
    fn flush(&mut self) -> Result<(), Error>;

    fn write_all(&mut self, buf: &[u8]) -> Result<(), Error>;
    fn write_fmt(&mut self, fmt: fmt::Arguments) -> Result<(), Error>;
}

Result<..., Error> diulang banyak. Oleh karena itu, std::io punya deklarasi type alias ini:

use std::fmt;

type Result<T> = std::result::Result<T, std::io::Error>;

pub trait Write {
    fn write(&mut self, buf: &[u8]) -> Result<usize>;
    fn flush(&mut self) -> Result<()>;

    fn write_all(&mut self, buf: &[u8]) -> Result<()>;
    fn write_fmt(&mut self, fmt: fmt::Arguments) -> Result<()>;
}

Karena deklarasi ini di modul std::io, kita bisa menggunakan alias fully qualified std::io::Result<T>; yaitu, Result<T, E> dengan E diisi sebagai std::io::Error. Tanda tangan fungsi trait Write akhirnya terlihat seperti ini:

use std::fmt;

type Result<T> = std::result::Result<T, std::io::Error>;

pub trait Write {
    fn write(&mut self, buf: &[u8]) -> Result<usize>;
    fn flush(&mut self) -> Result<()>;

    fn write_all(&mut self, buf: &[u8]) -> Result<()>;
    fn write_fmt(&mut self, fmt: fmt::Arguments) -> Result<()>;
}

Type alias membantu dalam dua cara: Ia membuat kode lebih mudah ditulis dan memberi kita interface yang konsisten di seluruh std::io. Karena itu alias, itu hanyalah Result<T, E> lain, yang berarti kita bisa menggunakan metode apa pun yang bekerja pada Result<T, E> dengannya, serta sintaks khusus seperti operator ?.

Never Type Yang Tidak Pernah Mengembalikan

Rust memiliki tipe khusus bernama ! yang dikenal dalam terminologi teori tipe sebagai empty type karena tidak punya nilai. Kami lebih suka menyebutnya never type karena ia berdiri di tempat tipe pengembalian saat fungsi tidak akan pernah mengembalikan. Ini contohnya:

fn bar() -> ! {
    // --snip--
    panic!();
}

Kode ini dibaca sebagai “fungsi bar mengembalikan never.” Fungsi yang mengembalikan never disebut diverging functions. Kita tidak bisa membuat nilai bertipe !, jadi bar tidak mungkin pernah mengembalikan.

Tapi apa gunanya tipe yang tidak bisa Anda buat nilainya? Ingat kode dari Listing 2-5, bagian dari game tebak angka; kami mereproduksi sedikit di sini di Listing 20-27.

Saat itu, kami melewati beberapa detail di kode ini. Di bagian “Konstruksi Alur Kontrol match” di Bab 6, kami membahas bahwa arm match harus semua mengembalikan tipe yang sama. Jadi, misalnya, kode berikut tidak bekerja:

fn main() {
    let guess = "3";
    let guess = match guess.trim().parse() {
        Ok(_) => 5,
        Err(_) => "hello",
    };
}

Tipe guess dalam kode ini harus integer dan string, dan Rust mewajibkan guess hanya punya satu tipe. Jadi, apa yang dikembalikan continue? Bagaimana kami diizinkan mengembalikan u32 dari satu arm dan punya arm lain yang berakhir dengan continue di Listing 20-27?

Seperti yang mungkin Anda duga, continue punya nilai !. Yaitu, saat Rust menghitung tipe guess, ia melihat kedua arm match, yang pertama dengan nilai u32 dan yang kedua dengan nilai !. Karena ! tidak pernah bisa punya nilai, Rust memutuskan bahwa tipe guess adalah u32.

Cara formal mendeskripsikan perilaku ini adalah ekspresi bertipe ! bisa di-coerce ke tipe lain apa pun. Kita diizinkan mengakhiri arm match ini dengan continue karena continue tidak mengembalikan nilai; alih-alih, ia memindahkan kontrol kembali ke atas loop, jadi di kasus Err, kita tidak pernah menetapkan nilai ke guess.

Never type berguna dengan makro panic! juga. Ingat fungsi unwrap yang kami panggil pada nilai Option<T> untuk menghasilkan nilai atau panic dengan definisi ini:

enum Option<T> {
    Some(T),
    None,
}

use crate::Option::*;

impl<T> Option<T> {
    pub fn unwrap(self) -> T {
        match self {
            Some(val) => val,
            None => panic!("called `Option::unwrap()` on a `None` value"),
        }
    }
}

Di kode ini, hal yang sama terjadi seperti di match di Listing 20-27: Rust melihat bahwa val bertipe T dan panic! bertipe !, jadi hasil dari keseluruhan ekspresi match adalah T. Kode ini bekerja karena panic! tidak menghasilkan nilai; ia mengakhiri program. Di kasus None, kita tidak akan mengembalikan nilai dari unwrap, jadi kode ini valid.

Satu ekspresi terakhir yang punya tipe ! adalah loop:

fn main() {
    print!("forever ");

    loop {
        print!("and ever ");
    }
}

Di sini, loop tidak pernah berakhir, jadi ! adalah nilai ekspresi. Akan tetapi, ini tidak akan benar jika kita menyertakan break, karena loop akan berhenti saat sampai ke break.

Dynamically Sized Types dan Trait Sized

Rust butuh mengetahui detail tertentu tentang tipe-tipenya, seperti berapa ruang yang dialokasikan untuk nilai tipe tertentu. Ini meninggalkan satu sudut sistem tipenya sedikit membingungkan pada awalnya: konsep dynamically sized types. Kadang disebut DSTs atau unsized types, tipe-tipe ini memungkinkan kita menulis kode menggunakan nilai yang ukurannya hanya bisa kita ketahui pada runtime.

Mari selami detail tipe dynamically sized yang disebut str, yang kami gunakan sepanjang buku. Itu benar, bukan &str, tapi str sendiri, adalah DST. Di banyak kasus, seperti saat menyimpan teks yang dimasukkan pengguna, kita tidak bisa tahu panjang string sampai runtime. Artinya kita tidak bisa membuat variabel bertipe str, dan tidak bisa mengambil argumen bertipe str. Pertimbangkan kode berikut, yang tidak bekerja:

fn main() {
    let s1: str = "Hello there!";
    let s2: str = "How's it going?";
}

Rust butuh tahu berapa memori yang dialokasikan untuk nilai apa pun dari tipe tertentu, dan semua nilai dari sebuah tipe harus menggunakan jumlah memori yang sama. Jika Rust mengizinkan kita menulis kode ini, dua nilai str ini harus memakan ruang yang sama. Tapi mereka punya panjang berbeda: s1 butuh 12 byte penyimpanan dan s2 butuh 15. Inilah mengapa tidak mungkin membuat variabel yang menampung dynamically sized type.

Jadi, apa yang kita lakukan? Di kasus ini, Anda sudah tahu jawabannya: Kita membuat tipe s1 dan s2 menjadi string slice (&str) alih-alih str. Ingat dari bagian “String Slices” di Bab 4 bahwa struktur data slice hanya menyimpan posisi awal dan panjang slice. Jadi, meski &T adalah nilai tunggal yang menyimpan alamat memori di mana T berada, string slice adalah dua nilai: alamat str dan panjangnya. Sebagai gantinya, kita bisa mengetahui ukuran nilai string slice pada waktu kompilasi: Ia dua kali panjang usize. Yaitu, kita selalu tahu ukuran string slice, tidak peduli sepanjang apa string yang dirujuknya. Secara umum, inilah cara dynamically sized types digunakan di Rust: Mereka memiliki tambahan metadata yang menyimpan ukuran informasi dinamis. Aturan emas dynamically sized types adalah kita harus selalu meletakkan nilai dynamically sized types di balik pointer semacamnya.

Kita bisa mengkombinasikan str dengan semua jenis pointer: misalnya, Box<str> atau Rc<str>. Faktanya, Anda sudah melihat ini sebelumnya tapi dengan dynamically sized type yang berbeda: trait. Setiap trait adalah dynamically sized type yang bisa kita rujuk dengan menggunakan nama trait. Di bagian “Menggunakan Trait Objects untuk Mengabstraksi Perilaku Bersama” di Bab 18, kami menyebutkan bahwa untuk menggunakan trait sebagai trait objects, kita harus meletakkannya di balik pointer, seperti &dyn Trait atau Box<dyn Trait> (Rc<dyn Trait> juga akan bekerja).

Untuk bekerja dengan DST, Rust menyediakan trait Sized untuk menentukan apakah ukuran tipe diketahui pada waktu kompilasi. Trait ini secara otomatis diimplementasikan untuk semua hal yang ukurannya diketahui pada waktu kompilasi. Di samping itu, Rust secara implisit menambahkan bound pada Sized ke setiap fungsi generik. Yaitu, definisi fungsi generik seperti ini:

fn generic<T>(t: T) {
    // --snip--
}

sebenarnya diperlakukan seolah-olah kita menulis ini:

fn generic<T: Sized>(t: T) {
    // --snip--
}

Secara default, fungsi generik hanya akan bekerja pada tipe yang memiliki ukuran diketahui pada waktu kompilasi. Akan tetapi, Anda bisa menggunakan sintaks khusus berikut untuk melonggarkan batasan ini:

fn generic<T: ?Sized>(t: &T) {
    // --snip--
}

Trait bound pada ?Sized berarti “T mungkin atau tidak Sized,” dan notasi ini meng-override default bahwa tipe generik harus punya ukuran diketahui pada waktu kompilasi. Sintaks ?Trait dengan arti ini hanya tersedia untuk Sized, bukan trait lain.

Perhatikan juga bahwa kami menukar tipe parameter t dari T ke &T. Karena tipe mungkin tidak Sized, kita perlu menggunakannya di balik semacam pointer. Di kasus ini, kami memilih referensi.

Selanjutnya, kami akan membahas fungsi dan closure!
