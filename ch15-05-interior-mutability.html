The Rust Programming Language

RefCell<T> dan Pola Interior Mutability

Interior mutability (mutabilitas interior) adalah pola desain di Rust yang memungkinkan Anda memutasi data bahkan saat ada referensi immutable ke data itu; normalnya, aksi ini dilarang oleh aturan peminjaman. Untuk memutasi data, pola ini menggunakan kode unsafe di dalam struktur data untuk melengkungkan aturan biasa Rust yang mengatur mutasi dan peminjaman. Kode unsafe menunjukkan ke compiler bahwa kami memeriksa aturan secara manual alih-alih mengandalkan compiler untuk memeriksa mereka untuk kami; kami akan membahas kode unsafe lebih lanjut di Bab 20.

Kami bisa menggunakan tipe yang menggunakan pola interior mutability hanya saat kami bisa memastikan bahwa aturan peminjaman akan diikuti pada runtime, meskipun compiler tidak bisa menjaminnya. Kode unsafe yang terlibat kemudian dibungkus dalam API yang aman, dan tipe luar tetap immutable.

Mari jelajahi konsep ini dengan melihat tipe RefCell<T> yang mengikuti pola interior mutability.

Menegakkan Aturan Peminjaman pada Runtime

Berbeda dengan Rc<T>, tipe RefCell<T> merepresentasikan kepemilikan tunggal atas data yang ditampungnya. Jadi, apa yang membuat RefCell<T> berbeda dari tipe seperti Box<T>? Ingat aturan peminjaman yang Anda pelajari di Bab 4:

  • Pada setiap waktu tertentu, Anda bisa memiliki baik satu referensi mutable atau sejumlah referensi immutable (tapi tidak keduanya).
  • Referensi harus selalu valid.

Dengan referensi dan Box<T>, invariant aturan peminjaman diberlakukan pada waktu kompilasi. Dengan RefCell<T>, invariant ini diberlakukan pada runtime. Dengan referensi, jika Anda melanggar aturan ini, Anda akan mendapat kesalahan compiler. Dengan RefCell<T>, jika Anda melanggar aturan ini, program Anda akan panic dan keluar.

Keuntungan memeriksa aturan peminjaman pada waktu kompilasi adalah kesalahan akan tertangkap lebih awal dalam proses pengembangan, dan tidak ada dampak pada performa runtime karena semua analisis diselesaikan sebelumnya. Untuk alasan-alasan ini, memeriksa aturan peminjaman pada waktu kompilasi adalah pilihan terbaik di kebanyakan kasus, itulah mengapa ini default Rust.

Keuntungan memeriksa aturan peminjaman pada runtime adalah skenario memory-safe tertentu menjadi diizinkan, di mana pemeriksaan waktu kompilasi melarangnya. Analisis statis, seperti compiler Rust, secara inherent bersifat konservatif. Beberapa properti kode tidak mungkin terdeteksi dengan menganalisis kode: Contoh paling terkenal adalah Halting Problem, yang di luar cakupan buku ini tapi topik menarik untuk diteliti.

Karena beberapa analisis tidak mungkin, jika compiler Rust tidak yakin kode mematuhi aturan kepemilikan, ia mungkin menolak program yang benar; dengan cara ini, ia bersifat konservatif. Jika Rust menerima program yang salah, pengguna tidak akan bisa mempercayai jaminan Rust. Akan tetapi, jika Rust menolak program yang benar, programmer akan merepotkan, tapi tidak ada yang katarostrof bisa terjadi. Tipe RefCell<T> berguna saat Anda yakin kode Anda mengikuti aturan peminjaman tapi compiler tidak paham dan menjaminnya.

Mirip dengan Rc<T>, RefCell<T> hanya untuk digunakan di skenario single-threaded dan akan memberi Anda kesalahan waktu kompilasi jika Anda mencoba menggunakannya di konteks multithreaded. Kami akan membahas cara mendapatkan fungsionalitas RefCell<T> di program multithreaded di Bab 16.

Berikut rangkuman alasan memilih Box<T>, Rc<T>, atau RefCell<T>:

  • Rc<T> memungkinkan beberapa pemilik data yang sama; Box<T> dan RefCell<T> memiliki pemilik tunggal.
  • Box<T> mengizinkan peminjaman immutable atau mutable yang diperiksa pada waktu kompilasi; Rc<T> mengizinkan hanya peminjaman immutable yang diperiksa pada waktu kompilasi; RefCell<T> mengizinkan peminjaman immutable atau mutable yang diperiksa pada runtime.
  • Karena RefCell<T> mengizinkan peminjaman mutable yang diperiksa pada runtime, Anda bisa memutasi nilai di dalam RefCell<T> bahkan saat RefCell<T> immutable.

Memutasi nilai di dalam nilai immutable adalah pola interior mutability. Mari lihat situasi di mana interior mutability berguna dan periksa bagaimana itu mungkin.

Menggunakan Interior Mutability

Konsekuensi dari aturan peminjaman adalah saat Anda memiliki nilai immutable, Anda tidak bisa meminjamnya secara mutable. Misalnya, kode ini tidak akan kompilasi:

fn main() {
    let x = 5;
    let y = &mut x;
}

Jika Anda mencoba mengompilasi kode ini, Anda akan mendapat kesalahan berikut:

$ cargo run
   Compiling borrowing v0.1.0 (file:///projects/borrowing)
error[E0596]: cannot borrow `x` as mutable, as it is not declared as mutable
 --> src/main.rs:3:13
  |
3 |     let y = &mut x;
  |             ^^^^^^ cannot borrow as mutable
  |
help: consider changing this to be mutable
  |
2 |     let mut x = 5;
  |         +++

For more information about this error, try `rustc --explain E0596`.
error: could not compile `borrowing` (bin "borrowing") due to 1 previous error

Akan tetapi, ada situasi di mana berguna bagi nilai untuk memutasi dirinya sendiri di metodenya tapi tampak immutable ke kode lain. Kode di luar metode nilai tidak akan bisa memutasi nilai. Menggunakan RefCell<T> adalah salah satu cara untuk mendapatkan kemampuan interior mutability, tapi RefCell<T> tidak mengelakkan aturan peminjaman sepenuhnya: Borrow checker di compiler mengizinkan interior mutability ini, dan aturan peminjaman diperiksa pada runtime aslinya. Jika Anda melanggar aturan, Anda akan mendapat panic! alih-alih kesalahan compiler.

Mari kerjakan contoh praktis di mana kami bisa menggunakan RefCell<T> untuk memutasi nilai immutable dan lihat mengapa itu berguna.

Pengujian dengan Mock Object

Terkadang saat pengujian programmer akan menggunakan tipe sebagai ganti tipe lain, untuk mengamati perilaku tertentu dan menegaskan bahwa itu diimplementasikan dengan benar. Tipe placeholder ini disebut test double. Bayangkan dalam arti stunt double di pembuatan film, di mana seseorang melangkah masuk dan menggantikan aktor untuk melakukan adegan yang terutama tricky. Test double menggantikan tipe lain saat kami menjalankan pengujian. Mock object adalah tipe spesifik dari test double yang mencatat apa yang terjadi selama pengujian sehingga Anda bisa menegaskan bahwa aksi yang benar telah terjadi.

Rust tidak memiliki objek dalam arti yang sama seperti bahasa lain memiliki objek, dan Rust tidak memiliki fungsionalitas mock object builtin di pustaka standar seperti beberapa bahasa lain. Akan tetapi, Anda pasti bisa membuat struct yang akan melayani tujuan yang sama sebagai mock object.

Inilah skenario yang akan kami uji: Kami akan membuat library yang melacak nilai terhadap nilai maksimum dan mengirim pesan berdasarkan seberapa dekat ke nilai maksimum nilai saat ini. Library ini bisa digunakan untuk melacak kuota pengguna untuk jumlah pemanggilan API yang diperbolehkan mereka buat, misalnya.

Library kami hanya akan menyediakan fungsionalitas melacak seberapa dekat nilai ke nilai maksimum dan pesan apa yang seharusnya dikirim pada waktu apa. Aplikasi yang menggunakan library kami akan diharapkan menyediakan mekanisme untuk mengirim pesan: Aplikasi bisa menampilkan pesan ke pengguna langsung, mengirim email, mengirim pesan teks, atau melakukan hal lain. Library tidak perlu tahu detail itu. Yang dibutuhkannya hanyalah sesuatu yang mengimplementasikan trait yang akan kami sediakan, bernama Messenger. Listing 15-20 menunjukkan kode library.

Satu bagian penting dari kode ini adalah trait Messenger memiliki satu metode bernama send yang mengambil referensi immutable ke self dan teks pesan. Trait ini adalah antarmuka yang mock object kami butuh implementasikan sehingga mock bisa digunakan dengan cara yang sama seperti objek asli. Bagian penting lainnya adalah kami ingin menguji perilaku metode set_value pada LimitTracker. Kami bisa mengubah apa yang kami teruskan untuk parameter value, tapi set_value tidak mengembalikan apa pun untuk kami buat penegasan. Kami ingin bisa mengatakan bahwa jika kami membuat LimitTracker dengan sesuatu yang mengimplementasikan trait Messenger dan nilai tertentu untuk max, messenger diberitahu untuk mengirim pesan yang tepat saat kami meneruskan angka berbeda untuk value.

Kami butuh mock object yang, alih-alih mengirim email atau pesan teks saat kami memanggil send, hanya akan melacak pesan yang diberitahu untuk dikirim. Kami bisa membuat instance baru mock object, membuat LimitTracker yang menggunakan mock object, memanggil metode set_value pada LimitTracker, dan lalu memeriksa bahwa mock object memiliki pesan yang kami harapkan. Listing 15-21 menunjukkan upaya mengimplementasikan mock object untuk melakukannya, tapi borrow checker tidak mengizinkannya.

Kode pengujian ini mendefinisikan struct MockMessenger yang memiliki bidang sent_messages dengan Vec nilai String untuk melacak pesan yang diberitahu untuk dikirim. Kami juga mendefinisikan fungsi terkait new untuk memudahkan membuat nilai MockMessenger baru yang dimulai dengan daftar pesan kosong. Kami lalu mengimplementasikan trait Messenger untuk MockMessenger sehingga kami bisa memberikan MockMessenger ke LimitTracker. Di definisi metode send, kami mengambil pesan yang diteruskan sebagai parameter dan menyimpannya ke daftar sent_messages MockMessenger.

Di pengujian, kami menguji apa yang terjadi saat LimitTracker diberitahu untuk menetapkan value ke sesuatu yang lebih dari 75 persen dari nilai max. Pertama, kami membuat MockMessenger baru, yang akan memulai dengan daftar pesan kosong. Lalu, kami membuat LimitTracker baru dan memberinya referensi ke MockMessenger baru dan nilai max 100. Kami memanggil metode set_value pada LimitTracker dengan nilai 80, yang lebih dari 75 persen dari 100. Lalu, kami menegaskan bahwa daftar pesan yang dilacak MockMessenger seharusnya kini memiliki satu pesan di dalamnya.

Akan tetapi, ada satu masalah dengan pengujian ini, seperti yang ditampilkan di sini:

Kami tidak bisa memodifikasi MockMessenger untuk melacak pesan, karena metode send mengambil referensi immutable ke self. Kami juga tidak bisa mengikuti saran dari teks kesalahan untuk menggunakan &mut self di baik metode impl maupun definisi trait. Kami tidak ingin mengubah trait Messenger hanya demi pengujian. Sebagai gantinya, kami perlu menemukan cara membuat kode pengujian kami bekerja dengan benar dengan desain yang sudah ada.

Ini situasi di mana interior mutability bisa membantu! Kami akan menyimpan sent_messages di dalam RefCell<T>, dan lalu metode send akan bisa memodifikasi sent_messages untuk menyimpan pesan yang kami lihat. Listing 15-22 menunjukkan seperti apa itu.

Bidang sent_messages kini bertipe RefCell<Vec<String>> alih-alih Vec<String>. Di fungsi new, kami membuat instance RefCell<Vec<String>> baru di sekeliling vektor kosong.

Untuk implementasi metode send, parameter pertamanya tetap referensi immutable borrow self, yang cocok dengan definisi trait. Kami memanggil borrow_mut pada RefCell<Vec<String>> di self.sent_messages untuk mendapatkan referensi mutable ke nilai di dalam RefCell<Vec<String>>, yaitu vektornya. Lalu, kami bisa memanggil push pada referensi mutable ke vektor untuk melacak pesan yang dikirim selama pengujian.

Perubahan terakhir yang harus kami buat adalah di penegasan: Untuk melihat berapa banyak item di vektor internal, kami memanggil borrow pada RefCell<Vec<String>> untuk mendapatkan referensi immutable ke vektor.

Sekarang setelah Anda melihat cara menggunakan RefCell<T>, mari sedikit menggali bagaimana cara kerjanya!

Melacak Peminjaman pada Runtime

Saat membuat referensi immutable dan mutable, kami menggunakan sintaks & dan &mut, masing-masing. Dengan RefCell<T>, kami menggunakan metode borrow dan borrow_mut, yang merupakan bagian dari API aman yang milik RefCell<T>. Metode borrow mengembalikan tipe smart pointer Ref<T>, dan borrow_mut mengembalikan tipe smart pointer RefMut<T>. Kedua tipe mengimplementasikan Deref, sehingga kami bisa memperlakukan mereka seperti referensi biasa.

RefCell<T> melacak berapa banyak smart pointer Ref<T> dan RefMut<T> yang saat ini aktif. Setiap kali kami memanggil borrow, RefCell<T> menaikkan hitungan berapa banyak peminjaman immutable yang aktif. Saat nilai Ref<T> keluar dari ruang lingkup, hitungan peminjaman immutable turun 1. Sama seperti aturan peminjaman waktu kompilasi, RefCell<T> memungkinkan kami memiliki banyak peminjaman immutable atau satu peminjaman mutable pada setiap titik waktu.

Jika kami mencoba melanggar aturan ini, alih-alih mendapat kesalahan compiler seperti yang akan terjadi dengan referensi, implementasi RefCell<T> akan panic pada runtime. Listing 15-23 menunjukkan modifikasi implementasi send di Listing 15-22. Kami dengan sengaja mencoba membuat dua peminjaman mutable aktif untuk ruang lingkup yang sama untuk menggambarkan bahwa RefCell<T> mencegah kami melakukan ini pada runtime.

Kami membuat variabel one_borrow untuk smart pointer RefMut<T> yang dikembalikan dari borrow_mut. Lalu, kami membuat peminjaman mutable lain dengan cara yang sama di variabel two_borrow. Ini membuat dua referensi mutable di ruang lingkup yang sama, yang tidak diizinkan. Saat kami menjalankan pengujian untuk library kami, kode di Listing 15-23 akan kompilasi tanpa kesalahan apa pun, tapi pengujian akan gagal:

Perhatikan bahwa kode panic dengan pesan already borrowed: BorrowMutError. Inilah cara RefCell<T> menangani pelanggaran aturan peminjaman pada runtime.

Memilih untuk menangkap kesalahan peminjaman pada runtime alih-alih waktu kompilasi, seperti yang kami lakukan di sini, berarti Anda potensial menemukan kesalahan di kode Anda lebih lama dalam proses pengembangan: mungkin tidak sebelum kode Anda di-deploy ke production. Juga, kode Anda akan menanggung penalti performa runtime kecil sebagai akibat melacak peminjaman pada runtime alih-alih waktu kompilasi. Akan tetapi, menggunakan RefCell<T> memungkinkan penulisan mock object yang bisa memodifikasi dirinya sendiri untuk melacak pesan yang telah dilihat saat Anda menggunakannya di konteks di mana hanya nilai immutable yang diizinkan. Anda bisa menggunakan RefCell<T> meski trade-off-nya untuk mendapatkan fungsionalitas lebih dari yang disediakan referensi biasa.

Mengizinkan Beberapa Pemilik Data Mutable

Cara umum menggunakan RefCell<T> adalah dalam kombinas dengan Rc<T>. Ingat bahwa Rc<T> memungkinkan Anda memiliki beberapa pemilik beberapa data, tapi ia hanya memberikan akses immutable ke data itu. Jika Anda punya Rc<T> yang menampung RefCell<T>, Anda bisa mendapatkan nilai yang bisa memiliki beberapa pemilik dan yang bisa Anda mutasi!

Misalnya, ingat contoh cons list di Listing 15-18 di mana kami menggunakan Rc<T> untuk mengizinkan beberapa list berbagi kepemilikan list lain. Karena Rc<T> hanya menampung nilai immutable, kami tidak bisa mengubah nilai apapun di list setelah kami menciptakannya. Mari tambahkan RefCell<T> untuk kemampuannya mengubah nilai di list. Listing 15-24 menunjukkan bahwa dengan menggunakan RefCell<T> di definisi Cons, kami bisa memodifikasi nilai yang disimpan di semua list.

Kami membuat nilai yang adalah instance Rc<RefCell<i32>> dan menyimpannya di variabel bernama value sehingga kami bisa mengaksesnya langsung nanti. Lalu, kami membuat List di a dengan varian Cons yang menampung value. Kami perlu me-clone value sehingga baik a maupun value memiliki kepemilikan nilai internal 5 alih-alih mentransfer kepemilikan dari value ke a atau memiliki a meminjam dari value.

Kami membungkus list a dalam Rc<T> sehingga saat kami membuat list b dan c, keduanya bisa merujuk ke a, yang kami lakukan di Listing 15-18.

Setelah kami membuat list di a, b, dan c, kami ingin menambah 10 ke nilai di value. Kami melakukannya dengan memanggil borrow_mut pada value, yang menggunakan fitur dereferencing otomatis yang kami bahas di “Di Mana Operator ->?” Bab 5 untuk mendereference Rc<T> ke nilai RefCell<T> internal. Metode borrow_mut mengembalikan smart pointer RefMut<T>, dan kami menggunakan operator dereference padanya dan mengubah nilai internal.

Saat kami mencetak a, b, dan c, kami bisa melihat bahwa mereka semua memiliki nilai termodifikasi 15 bukannya 5:

$ cargo run
   Compiling cons-list v0.1.0 (file:///projects/cons-list)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.63s
     Running `target/debug/cons-list`
a after = Cons(RefCell { value: 15 }, Nil)
b after = Cons(RefCell { value: 3 }, Cons(RefCell { value: 15 }, Nil))
c after = Cons(RefCell { value: 4 }, Cons(RefCell { value: 15 }, Nil))

Teknik ini cukup keren! Dengan menggunakan RefCell<T>, kami memiliki nilai List yang secara kelihatannya immutable. Tapi kami bisa menggunakan metode pada RefCell<T> yang menyediakan akses ke interior mutability-nya sehingga kami bisa memodifikasi data kami saat kami butuh. Pemeriksaan aturan peminjaman pada runtime melindungi kami dari data race, dan ini terkadang layak tukar kecepatan sedikit dengan fleksibilitas ini di struktur data kami. Perhatikan bahwa RefCell<T> tidak berfungsi untuk kode multithreaded! Mutex<T> adalah versi thread-safe dari RefCell<T>, dan kami akan membahas Mutex<T> di Bab 16.
