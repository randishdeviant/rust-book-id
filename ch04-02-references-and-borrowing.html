The Rust Programming Language

Referensi dan Peminjaman

Masalah dengan kode tuple di Listing 4-5 adalah kami harus mengembalikan String ke fungsi pemanggil agar kami masih bisa menggunakan String setelah pemanggilan ke calculate_length, karena String di-move ke calculate_length. Sebagai gantinya, kami bisa menyediakan referensi ke nilai String. Referensi seperti pointer dalam arti ia adalah alamat yang bisa kami ikuti untuk mengakses data yang disimpan di alamat itu; data itu dimiliki oleh variabel lain. Berbeda dengan pointer, referensi dijamin menunjuk ke nilai valid dari tipe tertentu untuk masa hidup referensi itu.

Berikut cara mendefinisikan dan menggunakan fungsi calculate_length yang memiliki referensi ke sebuah objek sebagai parameter alih-alih mengambil kepemilikan nilai:

Pertama, perhatikan bahwa semua kode tuple di deklarasi variabel dan nilai kembali fungsi hilang. Kedua, perhatikan bahwa kami meneruskan &s1 ke calculate_length dan, di definisinya, kami mengambil &String bukan String. Ampersand-ampersand ini mewakili referensi, dan mereka memungkinkan Anda merujuk ke beberapa nilai tanpa mengambil kepemilikannya. Gambar 4-6 menggambarkan konsep ini.

Gambar 4-6: Diagram &String s yang menunjuk ke String s1

Catatan: Kebalikan dari referensi dengan menggunakan & adalah dereferencing, yang dilakukan dengan operator dereference, *. Kami akan melihat beberapa penggunaan operator dereference di Bab 8 dan membahas detail dereferencing di Bab 15.

Mari lihat lebih dekat pemanggilan fungsi di sini:

fn main() {
    let s1 = String::from("hello");

    let len = calculate_length(&s1);

    println!("The length of '{s1}' is {len}.");
}

fn calculate_length(s: &String) -> usize {
    s.len()
}

Sintaks &s1 memungkinkan kami membuat referensi yang merujuk ke nilai s1 tapi tidak memilikinya. Karena referensi tidak memilikinya, nilai yang ditunjuk tidak akan di-drop saat referensi berhenti digunakan.

Demikian pula, tanda tangan fungsi menggunakan & untuk menunjukkan bahwa tipe parameter s adalah referensi. Mari tambahkan beberapa anotasi penjelasan:

fn main() {
    let s1 = String::from("hello");

    let len = calculate_length(&s1);

    println!("The length of '{s1}' is {len}.");
}

fn calculate_length(s: &String) -> usize { // s is a reference to a String
    s.len()
} // Here, s goes out of scope. But because s does not have ownership of what
  // it refers to, the String is not dropped.

Ruang lingkup di mana variabel s valid sama dengan ruang lingkup parameter fungsi apa pun, tapi nilai yang ditunjuk referensi tidak di-drop saat s berhenti digunakan, karena s tidak memiliki kepemilikan. Saat fungsi memiliki referensi sebagai parameter alih-alih nilai aktual, kami tidak akan perlu mengembalikan nilai untuk mengembalikan kepemilikan, karena kami tidak pernah memiliki kepemilikannya.

Kami menyebut tindakan membuat referensi peminjaman (borrowing). Seperti di kehidupan nyata, jika seseorang memiliki sesuatu, Anda bisa meminjamnya darinya. Saat Anda selesai, Anda harus mengembalikannya. Anda tidak memilikinya.

Jadi, apa yang terjadi jika kami mencoba memodifikasi sesuatu yang kami pinjam? Coba kode di Listing 4-6. Spoiler alert: Tidak berfungsi!

Sama seperti variabel secara default tidak dapat diubah (immutable), begitu juga referensi. Kami tidak diizinkan memodifikasi sesuatu yang kami miliki referensinya.

Referensi Mutable (Dapat Diubah)

Kami bisa memperbaiki kode dari Listing 4-6 untuk memungkinkan kami memodifikasi nilai yang dipinjam hanya dengan beberapa perubahan kecil yang menggunakan, sebagai gantinya, referensi mutable:

Pertama, kami mengubah s menjadi mut. Lalu, kami membuat referensi mutable dengan &mut s di mana kami memanggil fungsi change dan memperbarui tanda tangan fungsi untuk menerima referensi mutable dengan some_string: &mut String. Ini membuat sangat jelas bahwa fungsi change akan memutasi nilai yang dipinjam.

Referensi mutable memiliki satu pembatasan besar: Jika Anda memiliki referensi mutable ke sebuah nilai, Anda tidak bisa memiliki referensi lain ke nilai itu. Kode ini yang mencoba membuat dua referensi mutable ke s akan gagal:

Ini kesalahannya:

$ cargo run
   Compiling ownership v0.1.0 (file:///projects/ownership)
error[E0499]: cannot borrow `s` as mutable more than once at a time
 --> src/main.rs:5:14
  |
4 |     let r1 = &mut s;
  |              ------ first mutable borrow occurs here
5 |     let r2 = &mut s;
  |              ^^^^^^ second mutable borrow occurs here
6 |
7 |     println!("{r1}, {r2}");
  |                -- first borrow later used here

For more information about this error, try `rustc --explain E0499`.
error: could not compile `ownership` (bin "ownership") due to 1 previous error

Kesalahan ini mengatakan bahwa kode ini tidak valid karena kami tidak bisa meminjam s sebagai mutable lebih dari sekali pada satu waktu. Peminjaman mutable pertama ada di r1 dan harus bertahan hingga digunakan di println!, tapi antara pembuatan referensi mutable itu dan penggunaannya, kami mencoba membuat referensi mutable lain di r2 yang meminjam data yang sama dengan r1.

Pembatasan yang mencegah beberapa referensi mutable ke data yang sama pada waktu yang sama memungkinkan mutasi tapi dengan cara yang sangat terkendali. Ini adalah hal yang diperjuangkan Rustacean baru karena kebanyakan bahasa membiarkan Anda memutasi kapan pun Anda mau. Keuntungan memiliki pembatasan ini adalah Rust bisa mencegah data race pada waktu kompilasi. Data race mirip dengan race condition dan terjadi ketika tiga perilaku ini terjadi:

  • Dua atau lebih pointer mengakses data yang sama pada waktu yang sama.
  • Setidaknya satu pointer digunakan untuk menulis ke data.
  • Tidak ada mekanisme yang digunakan untuk menyinkronkan akses ke data.

Data race menyebabkan perilaku tidak terdefinisi dan bisa sulit didiagnosis dan diperbaiki saat Anda mencoba melacaknya pada runtime; Rust mencegah masalah ini dengan menolak mengompilasi kode dengan data race!

Seperti biasa, kami bisa menggunakan tanda kurung kurawal untuk membuat ruang lingkup baru, memungkinkan beberapa referensi mutable, hanya tidak simultaneous (serentak):

fn main() {
    let mut s = String::from("hello");

    {
        let r1 = &mut s;
    } // r1 goes out of scope here, so we can make a new reference with no problems.

    let r2 = &mut s;
}

Rust menerapkan aturan serupa untuk menggabungkan referensi mutable dan immutable. Kode ini menghasilkan kesalahan:

fn main() {
    let mut s = String::from("hello");

    let r1 = &s; // no problem
    let r2 = &s; // no problem
    let r3 = &mut s; // BIG PROBLEM

    println!("{r1}, {r2}, and {r3}");
}

Ini kesalahannya:

$ cargo run
   Compiling ownership v0.1.0 (file:///projects/ownership)
error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
 --> src/main.rs:6:14
  |
4 |     let r1 = &s; // no problem
  |              -- immutable borrow occurs here
5 |     let r2 = &s; // no problem
6 |     let r3 = &mut s; // BIG PROBLEM
  |              ^^^^^^ mutable borrow occurs here
7 |
8 |     println!("{r1}, {r2}, and {r3}");
  |                -- immutable borrow later used here

For more information about this error, try `rustc --explain E0502`.
error: could not compile `ownership` (bin "ownership") due to 1 previous error

Phew! Kami juga tidak bisa memiliki referensi mutable selagi kami memiliki referensi immutable ke nilai yang sama.

Pengguna referensi immutable tidak mengharapkan nilai tiba-tiba berubah di bawah mereka! Akan tetapi, beberapa referensi immutable diizinkan karena tidak ada yang hanya membaca data yang memiliki kemampuan mempengaruhi pembacaan data orang lain.

Perhatikan bahwa ruang lingkup referensi dimulai dari tempat diperkenalkannya dan berlanjut hingga terakhir kali referensi itu digunakan. Misalnya, kode ini akan kompilasi karena penggunaan terakhir referensi immutable ada di println!, sebelum referensi mutable diperkenalkan:

fn main() {
    let mut s = String::from("hello");

    let r1 = &s; // no problem
    let r2 = &s; // no problem
    println!("{r1} and {r2}");
    // Variables r1 and r2 will not be used after this point.

    let r3 = &mut s; // no problem
    println!("{r3}");
}

Ruang lingkup referensi immutable r1 dan r2 berakhir setelah println! di mana mereka terakhir digunakan, yang adalah sebelum referensi mutable r3 dibuat. Ruang lingkup ini tidak tumpang tindih, jadi kode ini diizinkan: Compiler bisa memberitahu bahwa referensi tidak lagi digunakan pada titik sebelum akhir ruang lingkup.

Meskipun kesalahan peminjaman mungkin menjengkelkan kadang-kadang, ingat bahwa itu adalah compiler Rust menunjuk potensi bug lebih awal (pada waktu kompilasi bukan pada runtime) dan menunjukkan tepat di mana masalahnya. Lalu, Anda tidak perlu melacak mengapa data Anda bukan apa yang Anda pikirkan.

Referensi Dangling (Gantung)

Di bahasa dengan pointer, mudah sekali secara keliru membuat dangling pointer—pointer yang merujuk ke lokasi di memori yang mungkin sudah diberikan ke orang lain—dengan membebaskan beberapa memori sambil mempertahankan pointer ke memori itu. Di Rust, sebaliknya, compiler menjamin bahwa referensi tidak pernah akan menjadi referensi dangling: Jika Anda memiliki referensi ke beberapa data, compiler akan memastikan data itu tidak akan keluar dari ruang lingkup sebelum referensi ke data itu.

Mari coba buat referensi dangling untuk melihat bagaimana Rust mencegahnya dengan kesalahan waktu kompilasi:

Ini kesalahannya:

$ cargo run
   Compiling ownership v0.1.0 (file:///projects/ownership)
error[E0106]: missing lifetime specifier
 --> src/main.rs:5:16
  |
5 | fn dangle() -> &String {
  |                ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but there is no value for it to be borrowed from
help: consider using the `'static` lifetime, but this is uncommon unless you're returning a borrowed value from a `const` or a `static`
  |
5 | fn dangle() -> &'static String {
  |                 +++++++
help: instead, you are more likely to want to return an owned value
  |
5 - fn dangle() -> &String {
5 + fn dangle() -> String {
  |

For more information about this error, try `rustc --explain E0106`.
error: could not compile `ownership` (bin "ownership") due to 1 previous error

Pesan kesalahan ini merujuk ke fitur yang belum kami bahas: lifetime. Kami akan membahas lifetime detail di Bab 10. Tapi, jika Anda mengabaikan bagian tentang lifetime, pesan ini mengandung kunci mengapa kode ini bermasalah:

this function's return type contains a borrowed value, but there is no value
for it to be borrowed from

Mari lihat lebih dekat tepat apa yang terjadi pada setiap tahap kode dangle kami:

Karena s dibuat di dalam dangle, saat kode dangle selesai, s akan dealokasi. Tapi kami mencoba mengembalikan referensi ke itu. Artinya referensi ini akan menunjuk ke String yang tidak valid. Itu tidak bagus! Rust tidak akan biarkan kami melakukannya.

Solusinya di sini adalah mengembalikan String langsung:

fn main() {
    let string = no_dangle();
}

fn no_dangle() -> String {
    let s = String::from("hello");

    s
}

Ini berfungsi tanpa masalah. Kepemilikan dipindahkan keluar, dan tidak ada yang dealokasi.

Aturan Referensi

Mari rangkum apa yang kami bahas tentang referensi:

  • Pada setiap waktu tertentu, Anda bisa memiliki baik satu referensi mutable atau sejumlah referensi immutable.
  • Referensi harus selalu valid.
