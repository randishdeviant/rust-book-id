Dari Single-Threaded ke Multithreaded Server

Saat ini, server akan memproses setiap permintaan secara bergantian, artinya ia tidak akan memproses koneksi kedua sampai koneksi pertama selesai diproses. Jika server menerima lebih banyak permintaan, eksekusi serial ini akan semakin tidak optimal. Jika server menerima permintaan yang butuh waktu lama diproses, permintaan berikutnya harus menunggu sampai permintaan lama selesai, bahkan jika permintaan baru bisa diproses cepat. Kami perlu memperbaikinya, tapi pertama kami akan melihat masalah ini beraksi.

Meningkatkan Throughput dengan Thread Pool

Thread pool adalah sekelompok thread yang di-spawn dan siap menunggu untuk menangani tugas. Saat program menerima tugas baru, ia menugaskan salah satu thread di pool ke tugas itu, dan thread itu akan memproses tugas. Thread tersisa di pool tersedia untuk menangani tugas lain yang masuk selama thread pertama memproses. Saat thread pertama selesai memproses tugasnya, ia dikembalikan ke pool thread idle, siap menangani tugas baru. Thread pool memungkinkan Anda memproses koneksi secara concurrent, meningkatkan throughput server Anda.

Kami akan membatasi jumlah thread di pool ke angka kecil untuk melindungi dari serangan DoS; jika program kami membuat thread baru untuk setiap permintaan saat masuk, seseorang yang membuat 10 juta permintaan ke server kami bisa mengacaukan dengan menggunakan semua resource server dan menghentikan pemrosesan permintaan.

Alih-alih spawn thread tak terbatas, maka kami akan memiliki jumlah thread tetap yang menunggu di pool. Permintaan yang masuk dikirim ke pool untuk diproses. Pool akan memelihara antrian permintaan masuk. Setiap thread di pool akan pop off permintaan dari antrian ini, menangani permintaan, dan lalu meminta antrian untuk permintaan lain. Dengan desain ini, kami bisa memproses hingga N permintaan secara concurrent, di mana N adalah jumlah thread. Jika setiap thread merespons permintaan yang berjalan lama, permintaan berikutnya masih bisa menumpuk di antrian, tapi kami telah meningkatkan jumlah permintaan berjalan lama yang bisa kami tangani sebelum mencapai titik itu.

Teknik ini hanyalah salah satu dari banyak cara meningkatkan throughput web server. Opsi lain yang mungkin Anda jelajahi adalah model fork/join, model async I/O single-threaded, dan model async I/O multithreaded. Jika Anda tertarik pada topik ini, Anda bisa membaca lebih lanjut tentang solusi lain dan mencoba mengimplementasikannya; dengan bahasa low-level seperti Rust, semua opsi ini mungkin.

Sebelum kami mulai mengimplementasikan thread pool, mari bicara tentang seperti apa menggunakan pool seharusnya. Saat Anda mencoba mendesain kode, menulis interface client terlebih dahulu bisa membantu mengarahkan desain Anda. Tulis API kode sehingga terstruktur dengan cara Anda ingin memanggilnya; lalu, implementasikan fungsionalitas di dalam struktur itu alih-alih mengimplementasikan fungsionalitas dan lalu mendesain public API.

Mirip dengan cara kami menggunakan test-driven development di proyek di Bab 12, kami akan menggunakan compiler-driven development di sini. Kami akan menulis kode yang memanggil fungsi yang kami inginkan, dan lalu kami akan melihat error dari compiler untuk menentukan apa yang harus kami ubah selanjutnya agar kode bekerja. Sebelum melakukan itu, namun, kami akan mengeksplorasi teknik yang tidak akan kami gunakan sebagai titik awal.

Mengirim Kode dari ThreadPool ke Thread

Kami meninggalkan komentar di loop for di Listing 21-14 mengenai pembuatan thread. Di sini, kami akan melihat bagaimana kami benar-benar membuat thread. Pustaka standar menyediakan thread::spawn sebagai cara membuat thread, dan thread::spawn mengharapkan mendapatkan kode yang harus dijalankan thread segera setelah thread dibuat. Akan tetapi, di kasus kami, kami ingin membuat thread dan membuat mereka menunggu kode yang akan kami kirim nanti. Implementasi thread pustaka standar tidak menyertakan cara untuk melakukannya; kami harus mengimplementasikannya manual.

Kami akan mengimplementasikan perilaku ini dengan memperkenalkan struktur data baru di antara ThreadPool dan thread yang akan mengelola perilaku baru ini. Kami akan menyebut struktur data ini Worker, yang adalah istilah umum di implementasi pooling. Worker mengambil kode yang perlu dijalankan dan menjalankan kode di thread-nya.

Bayangkan orang bekerja di dapur restoran: Pekerja menunggu sampai pesanan datang dari pelanggan, dan lalu mereka bertanggung jawab mengambil pesanan itu dan memenuhinya.

Alih-alih menyimpan vector instance JoinHandle<()> di thread pool, kami akan menyimpan instance struct Worker. Setiap Worker akan menyimpan satu instance JoinHandle<()>. Lalu, kami akan mengimplementasikan metode pada Worker yang akan mengambil closure kode untuk dijalankan dan mengirimkannya ke thread yang sudah berjalan untuk eksekusi. Kami juga akan memberi setiap Worker id sehingga kami bisa membedakan instance Worker yang berbeda di pool saat logging atau debugging.

Ini proses baru yang akan terjadi saat kami membuat ThreadPool. Kami akan mengimplementasikan kode yang mengirim closure ke thread setelah Worker disiapkan dengan cara ini:

  1. Definisikan struct Worker yang menampung id dan JoinHandle<()>.
  2. Ubah ThreadPool untuk menampung vector instance Worker.
  3. Definisikan fungsi Worker::new yang menerima nomor id dan mengembalikan instance Worker yang menampung id dan thread di-spawn dengan closure kosong.
  4. Di ThreadPool::new, gunakan counter loop for untuk generate id, buat Worker baru dengan id itu, dan simpan Worker di vector.

Mengirim Permintaan ke Thread Melalui Channel

Masalah selanjutnya yang akan kami hadapi adalah closure yang diberikan ke thread::spawn sama sekali tidak melakukan apa pun. Saat ini, kami mendapat closure yang ingin kami eksekusi di metode execute. Tapi kami perlu memberi thread::spawn closure untuk dijalankan saat kami membuat setiap Worker selama pembuatan ThreadPool.

Kami ingin struct Worker yang baru saja kami buat mengambil kode untuk dijalankan dari antrian yang dipegang di ThreadPool dan mengirim kode itu ke thread-nya untuk dijalankan.

Channel yang kami pelajari di Bab 16—cara sederhana berkomunikasi antara dua thread—akan sempurna untuk kasus penggunaan ini. Kami akan menggunakan channel untuk berfungsi sebagai antrian pekerjaan, dan execute akan mengirim pekerjaan dari ThreadPool ke instance Worker, yang akan mengirim pekerjaan ke thread-nya. Ini rencananya:

  1. ThreadPool akan membuat channel dan memegang sender-nya.
  2. Setiap Worker akan memegang receiver-nya.
  3. Kami akan membuat struct Job baru yang akan menampung closure yang kami ingin kirim ke channel.
  4. Metode execute akan mengirim pekerjaan yang ingin dieksekusi melalui sender.
  5. Di thread-nya, Worker akan loop di atas receiver-nya dan mengeksekusi closure dari pekerjaan apa pun yang diterima.

Mari mulai dengan membuat channel di ThreadPool::new dan memegang sender di instance ThreadPool, seperti yang ditampilkan di Listing 21-16. Struct Job belum menampung apa pun untuk sekarang tapi akan jadi tipe item yang kami kirim ke channel.

Di ThreadPool::new, kami membuat channel baru dan membuat pool memegang sender. Ini akan kompilasi sukses.

Mari coba meneruskan receiver channel ke setiap Worker saat thread pool membuat channel. Kami tahu kami ingin menggunakan receiver di thread yang di-spawn instance Worker, jadi kami akan mereferensikan parameter receiver di closure. Kode di Listing 21-17 belum akan kompilasi.

Kami juga tidak ingin mengirim pesan beberapa kali ke beberapa consumer; kami ingin satu daftar pesan dengan beberapa instance Worker sehingga setiap pesan diproses sekali.

Di samping itu, mengambil pekerjaan dari antrian channel melibatkan memutasi receiver, jadi thread butuh cara aman untuk berbagi dan memodifikasi receiver; jika tidak, kami mungkin mendapat race conditions (seperti yang dibahas di Bab 16).

Ingat thread-safe smart pointers yang dibahas di Bab 16: Untuk berbagi kepemilikan di beberapa thread dan mengizinkan thread memutasi nilai, kami perlu menggunakan Arc<Mutex<T>>. Tipe Arc akan mengizinkan beberapa instance Worker memiliki receiver, dan Mutex akan memastikan hanya satu Worker yang mendapat pekerjaan dari receiver pada satu waktu. Listing 21-18 menunjukkan perubahan yang perlu kami buat.

Di ThreadPool::new, kami meletakkan receiver di Arc dan Mutex. Untuk setiap Worker baru, kami clone Arc untuk menaikkan reference count sehingga instance Worker bisa berbagi kepemilikan receiver.

Dengan perubahan ini, kode kompilasi! Kami mendekati tujuan!

Mengimplementasikan Metode execute

Mari akhirnya mengimplementasikan metode execute pada ThreadPool. Kami juga akan mengubah Job dari struct ke type alias untuk trait object yang menampung tipe closure yang execute terima. Seperti yang dibahas di bagian “Sinonim Tipe dan Type Aliases” di Bab 20, type aliases memungkinkan kami membuat tipe panjang lebih pendek untuk kemudahan penggunaan. Lihat Listing 21-19.

Setelah membuat instance Job baru menggunakan closure yang kami dapatkan di execute, kami mengirim pekerjaan itu ke ujung pengirim channel. Kami memanggil unwrap pada send untuk kasus pengiriman gagal. Ini mungkin terjadi jika, misalnya, kami menghentikan semua thread dari eksekusi, artinya receiving end telah berhenti menerima pesan baru. Saat ini, kami tidak bisa menghentikan thread kami dari eksekusi: Thread kami terus mengeksekusi selama pool ada. Alasan kami menggunakan unwrap adalah kami tahu kasus kegagalan tidak akan terjadi, tapi compiler tidak tahu itu.

Tapi kami belum selesai! Di Worker, closure kami yang diteruskan ke thread::spawn masih hanya mereferensikan receiving end channel. Sebagai gantinya, kami butuh closure untuk loop selamanya, meminta receiving end channel untuk pekerjaan dan menjalankan pekerjaan saat mendapatkannya. Mari buat perubahan yang ditampilkan di Listing 21-20 ke Worker::new.

Di sini, kami pertama memanggil lock pada receiver untuk mengakuisisi mutex, dan lalu memanggil unwrap untuk panic pada error apa pun. Mengakuisisi lock mungkin gagal jika mutex dalam keadaan poisoned, yang bisa terjadi jika thread lain panic saat memegang lock bukannya melepaskan lock. Dalam situasi ini, memanggil unwrap untuk membuat thread ini panic adalah tindakan yang benar. Bebas ubah unwrap ini ke expect dengan pesan error yang bermakna bagi Anda.

Jika kami mendapat lock pada mutex, kami memanggil recv untuk menerima Job dari channel. unwrap final melewati error di sini juga, yang mungkin terjadi jika thread yang memegang sender telah shutdown, mirip dengan cara metode send mengembalikan Err jika receiver shutdown.

Pemanggilan recv akan block, jadi jika belum ada pekerjaan, thread saat ini akan menunggu sampai pekerjaan tersedia. Mutex<T> memastikan hanya satu thread Worker pada satu waktu yang mencoba meminta pekerjaan.

Setelah mempelajari loop while let di Bab 17 dan Bab 19, Anda mungkin bertanya-tanya mengapa kami tidak menulis kode thread Worker seperti yang ditampilkan di Listing 21-21.

Kode ini kompilasi dan berjalan tapi tidak menghasilkan perilaku threading yang diinginkan: Permintaan lambat tetap akan menyebabkan permintaan lain menunggu diproses. Alasannya agak halus: Struct Mutex tidak punya metode unlock publik karena kepemilikan lock berbasis pada lifetime MutexGuard<T> di dalam LockResult<MutexGuard<T>> yang dikembalikan metode lock. Pada waktu kompilasi, borrow checker bisa lalu menegakkan aturan bahwa resource yang dijaga Mutex tidak bisa diakses kecuali kami memegang lock. Akan tetapi, implementasi ini juga bisa mengakibatkan lock dipegang lebih lama dari yang diinginkan jika kami tidak memperhatikan lifetime MutexGuard<T>.

Kode di Listing 21-20 yang menggunakan let job = receiver.lock().unwrap().recv().unwrap(); bekerja karena dengan let, nilai temporary apa pun yang digunakan di ekspresi di sisi kanan tanda sama dengan segera di-drop saat pernyataan let berakhir. Akan tetapi, while let (dan if let dan match) tidak me-drop nilai temporary sampai akhir blok terkait. Di Listing 21-21, lock tetap dipegang selama durasi pemanggilan job(), artinya instance Worker lain tidak bisa menerima pekerjaan.
