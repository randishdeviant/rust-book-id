The Rust Programming Language

Menelusuri Lebih Dalam Trait untuk Async

Sepanjang bab ini, kami telah menggunakan trait Future, Stream, dan StreamExt dengan berbagai cara. Sejauh ini, bagaimanapun, kami menghindari masuk terlalu dalam ke detail cara kerjanya atau bagaimana mereka cocok bersama, yang baik-baik saja untuk pekerjaan Rust sehari- hari Anda. Terkadang, bagaimanapun, Anda akan menemukan situasi di mana Anda perlu memahami beberapa detail lebih lanjut dari trait-trait ini, bersama dengan tipe Pin dan trait Unpin. Di bagian ini, kami akan menggali cukup dalam untuk membantu di skenario-skenario tersebut, masih meninggalkan deep dive yang benar-benar dalam untuk dokumentasi lain.

Trait Future

Mari mulai dengan melihat lebih dekat bagaimana trait Future bekerja. Inilah definisinya di Rust:

#![allow(unused)]
fn main() {
use std::pin::Pin;
use std::task::{Context, Poll};

pub trait Future {
    type Output;

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
}

Definisi trait ini mencakup banyak tipe baru dan juga beberapa sintaks yang belum pernah kami lihat sebelumnya, jadi mari bedah definisinya potong per potong.

Pertama, associated type Output milik Future mengatakan apa yang future resolve ke. Ini analog dengan associated type Item untuk trait Iterator. Kedua, Future punya metode poll, yang mengambil referensi Pin khusus untuk parameter self-nya dan referensi mutable ke tipe Context, dan mengembalikan Poll<Self::Output>. Kami akan bicara lebih lanjut tentang Pin dan Context sebentar lagi. Untuk saat ini, mari fokus pada apa yang dikembalikan metode, tipe Poll:

#![allow(unused)]
fn main() {
pub enum Poll<T> {
    Ready(T),
    Pending,
}
}

Tipe Poll ini mirip dengan Option. Ia punya satu varian yang punya nilai, Ready(T), dan satu yang tidak, Pending. Poll berarti hal yang cukup berbeda dari Option, bagaimanpun! Varian Pending menunjukkan bahwa future masih punya pekerjaan untuk dilakukan, sehingga pemanggil perlu memeriksa lagi nanti. Varian Ready menunjukkan bahwa Future telah menyelesaikan pekerjaannya dan nilai T tersedia.

Catatan: Jarang perlu memanggil poll langsung, tapi jika Anda perlu, ingat bahwa dengan kebanyakan future, pemanggil seharusnya tidak memanggil poll lagi setelah future mengembalikan Ready. Banyak future akan panic jika di-poll lagi setelah menjadi ready. Future yang aman di-poll lagi akan menyebutkannya secara eksplisit di dokumentasinya. Ini mirip dengan perilaku Iterator::next.

Saat Anda melihat kode yang menggunakan await, Rust mengompilkan di bawah tabir menjadi kode yang memanggil poll. Jika Anda melihat kembali Listing 17-4, di mana kami mencetak title halaman untuk satu URL begitu resolve, Rust mengompilasinya menjadi sesuatu seperti (tapi tidak persis) ini:

match page_title(url).poll() {
    Ready(page_title) => match page_title {
        Some(title) => println!("The title for {url} was {title}"),
        None => println!("{url} had no title"),
    }
    Pending => {
        // Tapi apa yang di sini?
    }
}

Apa yang seharusnya kami lakukan saat future masih Pending? Kami butuh cara untuk mencoba lagi, dan lagi, dan lagi, sampai future akhirnya siap. Dengan kata lain, kami butuh loop:

let mut page_title_fut = page_title(url);
loop {
    match page_title_fut.poll() {
        Ready(value) => match page_title {
            Some(title) => println!("The title for {url} was {title}"),
            None => println!("{url} had no title"),
        }
        Pending => {
            // lanjut
        }
    }
}

Jika Rust mengompilkan ke kode persis itu, bagaimanpun, setiap await akan blocking—persis kebalikan dari yang kami tuju! Sebagai gantinya, Rust memastikan bahwa loop bisa menyerahkan kontrol ke sesuatu yang bisa menjeda pekerjaan pada future ini untuk bekerja pada future lain dan lalu memeriksa ini lagi nanti. Seperti yang kami lihat, something itu adalah async runtime, dan penjadwalan dan koordinasi ini adalah salah satu pekerjaan utamanya.

Di bagian “Mengirim Data Antar Dua Task Menggunakan Message Passing”, kami mendeskripsikan menunggu pada rx.recv. Pemanggilan recv mengembalikan future, dan await future mem-poll-nya. Kami mencatat bahwa runtime akan menjeda future sampai siap dengan Some(message) atau None saat channel tertutup. Dengan pemahaman lebih dalam tentang trait Future, khususnya Future::poll, kami bisa melihat bagaimana itu bekerja. Runtime tahu future belum siap saat ia mengembalikan Poll::Pending. Sebaliknya, runtime tahu future sudah siap dan memajukannya saat poll mengembalikan Poll::Ready(Some(message)) atau Poll::Ready(None).

Detail persis bagaimana runtime melakukan itu di luar cakupan buku ini, tapi kuncinya adalah melihat mekanika dasar future: runtime mem-poll setiap future yang jadi tanggung jawabnya, meletakkan future tidur kembali saat belum siap.

Tipe Pin dan Trait Unpin

Kembali ke Listing 17-13, kami menggunakan makro trpl::join! untuk await tiga future. Akan tetapi, umum memiliki koleksi seperti vektor yang berisi sejumlah future yang tidak akan diketahui sampai runtime. Mari ubah Listing 17-13 ke kode di Listing 17-23 yang menaruh tiga future ke vektor dan memanggil fungsi trpl::join_all sebagai gantinya, yang belum akan kompilasi.

Kami menaruh setiap future di dalam Box untuk membuat mereka jadi trait objects, sama seperti yang kami lakukan di bagian “Mengembalikan Kesalahan dari run” Bab 12. (Kami akan membahas trait objects detail di Bab 18.) Menggunakan trait objects memungkinkan kami memperlakukan setiap future anonim yang dihasilkan tipe-tipe ini sebagai tipe yang sama, karena semua mereka mengimplementasikan trait Future.

Ini mungkin mengejutkan. Bagaimanpun, tidak satu pun dari blok async mengembalikan apa pun, jadi masing-masing menghasilkan Future<Output = ()>. Ingat bahwa Future adalah trait, bagaimanpun, dan compiler menciptakan enum unik untuk setiap blok async, bahkan saat mereka punya tipe output yang identik. Sama seperti Anda tidak bisa menaruh dua struct handwritten yang berbeda di Vec, Anda tidak bisa mencampur enum yang dihasilkan compiler.

Lalu kami meneruskan koleksi future ke fungsi trpl::join_all dan await hasilnya. Akan tetapi, ini tidak kompilasi; ini bagian relevan dari pesan kesalahan.

Catatan di pesan kesalahan ini memberitahu kami bahwa kami seharusnya menggunakan makro pin! untuk pin nilai, yang berarti menaruh mereka di dalam tipe Pin yang menjamin nilai tidak akan dipindahkan di memori. Pesan kesalahan mengatakan pinning diperlukan karena dyn Future<Output = ()> perlu mengimplementasikan trait Unpin dan saat ini tidak.

Fungsi trpl::join_all mengembalikan struct yang disebut JoinAll. Struct itu generik atas tipe F, yang dibatasi mengimplementasikan trait Future. Langsung await future dengan await mem-pin future secara implisit. Itu sebabnya kami tidak perlu menggunakan pin! di mana-mana kami ingin await future.

Akan tetapi, di sini kami tidak langsung await future. Sebagai gantinya, kami membangun future baru, JoinAll, dengan meneruskan koleksi future ke fungsi join_all. Tanda tangan untuk join_all mewajibkan tipe item di koleksi semuanya mengimplementasikan trait Future, dan Box<T> mengimplementasikan Future hanya jika T yang dibungkus adalah future yang mengimplementasikan trait Unpin.

Itu banyak untuk diserap! Untuk benar-benar memahaminya, mari selami sedikit lebih jauh cara kerja trait Future sebenarnya, khususnya soal pinning. Lihat lagi definisi trait Future:

#![allow(unused)]
fn main() {
use std::pin::Pin;
use std::task::{Context, Poll};

pub trait Future {
    type Output;

    // Required method
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
}

Parameter cx dan tipe Context-nya adalah kunci bagaimana runtime sebenarnya tahu kapan memeriksa future manapun sambil tetap lazy. Lagi, detail persis bagaimana itu bekerja di luar cakupan bab ini, dan Anda umumnya hanya perlu memikirkannya saat menulis implementasi Future kustom. Kami akan fokus sebagai gantinya pada tipe untuk self, karena ini pertama kalinya kami melihat metode di mana self punya anotasi tipe. Anotasi tipe untuk self bekerja seperti anotasi tipe untuk parameter fungsi lain tapi dengan dua perbedaan kunci:

  • Ia memberitahu Rust tipe apa self harusnya agar metode bisa dipanggil.
  • Ia tidak bisa sembarang tipe. Ia dibatasi pada tipe yang metodenya diimplementasikan, referensi atau smart pointer ke tipe itu, atau Pin yang membungkus referensi ke tipe itu.

Kami akan lihat lebih lanjut sintaks ini di Bab 18. Untuk sekarang, cukup tahu bahwa jika kami ingin mem-poll future untuk memeriksa apakah Pending atau Ready(Output), kami butuh referensi mutable Pin-wrapped ke tipe itu.

Pin adalah wrapper untuk tipe seperti pointer seperti &, &mut, Box, dan Rc. (Secara teknis, Pin bekerja dengan tipe yang mengimplementasikan trait Deref atau DerefMut, tapi ini efektifnya ekuivalen dengan hanya bekerja dengan referensi dan smart pointer.) Pin bukan pointer itu sendiri dan tidak punya perilaku sendiri seperti Rc dan Arc yang melakukan reference counting; ia murni alat yang compiler bisa gunakan untuk menegakkan batasan pada penggunaan pointer.

Mengingat bahwa await diimplementasikan dalam hal pemanggilan poll mulai menjelaskan pesan kesalahan yang kami lihat sebelumnya, tapi itu dalam hal Unpin, bukan Pin. Jadi bagaimana tepatnya Pin berhubungan dengan Unpin, dan mengapa Future butuh self berada di tipe Pin untuk memanggil poll?

Ingat dari awal bab ini bahwa serangkaian await point di future dikompilasi menjadi mesin state, dan compiler memastikan mesin state itu mengikuti semua aturan normal Rust seputar keamanan, termasuk borrowing dan kepemilikan. Agar itu berfungsi, Rust melihat data apa yang dibutuhkan antara satu await point dan await point berikutnya atau akhir blok async. Ia lalu menciptakan varian yang sesuai di mesin state terkompilasi. Masing-masing varian mendapat akses yang dibutuhkan ke data yang akan digunakan di bagian kode sumber itu, apakah dengan mengambil kepemilikan data itu atau dengan mendapatkan referensi mutable atau immutable ke nya.

Sejauh ini, bagus: jika kami salah soal kepemilikan atau referensi di blok async yang diberikan, borrow checker akan memberitahu kami. Saat kami ingin memindahkan future yang sesuai dengan blok tersebut—seperti memindahkannya ke Vec untuk digunakan sebagai iterator dengan join_all—hal jadi lebih rumit.

Saat kami memindahkan future—apakah dengan mendorongnya ke struktur data untuk digunakan sebagai iterator dengan join_all atau dengan mengembalikannya dari fungsi—itu sebenarnya berarti memindahkan mesin state yang Rust buat untuk kami. Dan berbeda dengan kebanyakan tipe lain di Rust, future yang Rust buat untuk blok async bisa berakhir dengan referensi ke mereka sendiri di field varian mana pun, seperti yang ditampilkan di ilustrasi terderhana di Gambar 17-4.

Secara default, bagaimanpun, objek apa pun yang punya referensi ke diri sendiri tidak aman untuk dipindahkan, karena referensi selalu menunjuk ke alamat memori aktual dari apa pun yang mereka referensikan (lihat Gambar 17-5). Jika Anda memindahkan struktur data itu sendiri, referensi internal itu akan tertinggal menunjuk ke lokasi lama. Akan tetapi, lokasi memori itu sekarang tidak valid. Untuk satu hal, nilainya tidak akan diupdate saat Anda membuat perubahan ke struktur data. Untuk hal lain—yang lebih penting—komputer kini bebas menggunakan memori itu untuk tujuan lain! Anda bisa akhinya membaca data yang完全不相关 nanti.

Secara teoritis, compiler Rust bisa mencoba mengupdate setiap referensi ke objek kapanpun ia dipindahkan, tapi itu bisa menambah overhead performa banyak, terutama jika seluruh jaringan referensi butuh diupdate. Jika kami bisa sebagai gantinya memastikan struktur data yang dimaksud tidak bergerak di memori, kami tidak perlu mengupdate referensi manapun. Inilah persis fungsi borrow checker Rust: di kode safe, ia mencegah Anda memindahkan item apa pun dengan referensi aktif ke dalamnya.

Pin membangun di atas itu untuk memberi kami jaminan persis yang kami butuhkan. Saat kami pin nilai dengan membungkus pointer ke nilai itu di Pin, ia tidak bisa lagi berpindah. Dengan demikian, jika Anda punya Pin<Box<SomeType>>, Anda sebenarnya mem-pin nilai SomeType, bukan pointer Box. Gambar 17-6 mengilustrasikan proses ini.

Faktanya, pointer Box tetap bisa bergerak bebas. Ingat: kami peduli soal memastikan data yang akhirnya direferensikan tetap di tempat. Jika pointer bergerak, tapi data yang ditunjuknya di tempat yang sama, seperti di Gambar 17-7, tidak ada potensi masalah. (Sebagai latihan independen, lihat dokumen untuk tipe-tipe serta modul std::pin dan coba cari tahu bagaimana Anda akan melakukannya dengan Pin yang membungkus Box.) Kuncinya adalah tipe self-referential itu sendiri tidak bisa bergerak, karena ia masih pinned.

Akan tetapi, kebanyakan tipe sempurna aman untuk dipindahkan, bahkan jika mereka kebetulan di belakang pointer Pin. Kami hanya perlu memikirkan pinning saat item punya referensi internal. Nilai primitif seperti angka dan Boolean aman karena jelas mereka tidak punya referensi internal. Sebanyakan tipe yang biasa Anda gunakan di Rust juga tidak. Anda bisa memindahkan Vec, misalnya, tanpa khawatir. Mengikuti apa yang kami lihat sejauh ini, jika Anda punya Pin<Vec<String>>, Anda harus melakukan segalanya via API aman tapi terbatas yang disediakan Pin, bahkan Vec<String> selalu aman dipindahkan jika tidak ada referensi lain ke dalamnya. Kami butuh cara memberitahu compiler bahwa memindahkan item di kasus seperti ini oke—dan itulah Unpin muncul.

Unpin adalah marker trait, mirip dengan trait Send dan Sync yang kami lihat di Bab 16, dan dengan demikian tidak punya fungsi sendiri. Marker trait ada hanya untuk memberitahu compiler bahwa aman menggunakan tipe yang mengimplementasikan trait tertentu dalam konteks tertentu. Unpin memberitahu compiler bahwa suatu tipe tidak perlu menegakkan jaminan apapun tentang apakah nilai yang dimaksud bisa dipindahkan dengan aman.

Sama seperti Send dan Sync, compiler mengimplementasikan Unpin secara otomatis untuk semua tipe di mana ia bisa membuktikan aman. Kasus khusus, lagi mirip Send dan Sync, adalah di mana Unpin tidak diimplementasikan untuk tipe. Notasi untuk ini adalah impl !Unpin for SomeType, di mana SomeType adalah nama tipe yang memang butuh menegakkan jaminan itu agar aman kapanpun pointer ke tipe itu digunakan di Pin.

Dengan kata lain, ada dua hal untuk diingat soal hubungan antara Pin dan Unpin. Pertama, Unpin adalah kasus “normal”, dan !Unpin adalah kasus khusus. Kedua, apakah tipe mengimplementasikan Unpin atau !Unpin hanya penting saat Anda menggunakan pointer pinned ke tipe itu seperti Pin<&mut SomeType>.

Untuk membuatnya konkret, pikirkan String: ia punya panjang dan karakter Unicode yang menyusunnya. Kami bisa membungkus String di Pin, seperti yang terlihat di Gambar 17-8. Akan tetapi, String secara otomatis mengimplementasikan Unpin, seperti kebanyakan tipe lain di Rust.

Hasilnya, kami bisa melakukan hal yang akan ilegal jika String mengimplementasikan !Unpin sebagai gantinya, seperti mengganti satu string dengan yang lain di lokasi memori persis sama seperti di Gambar 17-9. Ini tidak melanggar kontrak Pin, karena String tidak punya referensi internal yang membuatnya tidak aman untuk dipindahkan. Itu persis alasannya mengimplementasikan Unpin bukannya !Unpin.

Sekarang kami paham cukup untuk memahami kesalahan yang dilaporkan untuk pemanggilan join_all itu kembali di Listing 17-23. Kami awalnya mencoba memindahkan future yang dihasilkan blok async ke Vec<Box<dyn Future<Output = ()>>>, tapi seperti yang kami lihat, future itu mungkin punya referensi internal, jadi mereka tidak otomatis mengimplementasikan Unpin. Begitu kami pin mereka, kami bisa memasukkan tipe Pin yang dihasilkan ke Vec, yakin bahwa data di bawah di future tidak akan dipindahkan. Listing 17-24 menunjukkan cara memperbaiki kode dengan memanggil makro pin! di mana masing-masing dari tiga future didefinisikan dan menyesuaikan tipe trait object.

Contoh ini kini kompilasi dan berjalan, dan kami bisa menambah atau menghapus future dari vektor pada runtime dan join那些所有.

Pin dan Unpin kebanyakan penting untuk membangun library level-rendah, atau saat Anda membangun runtime sendiri, bukannya untuk kode Rust sehari-hari. Saat Anda melihat trait ini di pesan kesalahan, bagaimanpun, kini Anda akan punya ide lebih baik cara memperbaiki kode Anda!

Catatan: Kombinasi Pin dan Unpin ini memungkinkan implementasi aman seluruh kelas tipe kompleks di Rust yang sebaliknya akan terbukti menantang karena mereka self-referential. Tipe yang butuh Pin muncul paling umum di async Rust hari ini, tapi sekali-sekali, Anda mungkin melihat mereka di konteks lain, juga.

Spesifik cara kerja Pin dan Unpin, dan aturan yang mereka wajib menegakkan, dibahas secara ekstensif di dokumentasi API std::pin, jadi jika Anda tertarik belajar lebih lanjut, itu tempat bagus untuk memulai.

Trait Stream

Sekarang setelah Anda pemahaman lebih dalam pada Future, Pin, dan trait Unpin, kami bisa mengalihkan perhatian ke trait Stream. Seperti yang Anda pelajari sebelumnya di bab ini, stream mirip dengan iterator asynchronous. Berbeda dengan Iterator dan Future, bagaimanpun, Stream tidak punya definisi di pustaka standar per penulisan ini, tapi ada definisi sangat umum dari crate futures yang digunakan di seluruh ekosistem.

Mari tinjau definisi trait Iterator dan Future sebelum melihat bagaimana trait Stream mungkin menggabungkannya. Dari Iterator, kami punya ide urutan: metode next-nya menyediakan Option<Self::Item>. Dari Future, kami punya ide kesiapan seiring waktu: metode poll-nya menyediakan Poll<Self::Output>. Untuk merepresentasikan urutan item yang menjadi siap seiring waktu, kami mendefinisikan trait Stream yang menggabungkan fitur-fitur itu:

#![allow(unused)]
fn main() {
use std::pin::Pin;
use std::task::{Context, Poll};

trait Stream {
    type Item;

    fn poll_next(
        self: Pin<&mut Self>,
        cx: &mut Context<'_>
    ) -> Poll<Option<Self::Item>>;
}
}

Trait Stream mendefinisikan associated type yang disebut Item untuk tipe item yang dihasilkan stream. Ini mirip Iterator, di mana bisa nol sampai banyak item, dan tidak seperti Future, di mana selalu ada Output tunggal, bahkan jika tipe unit ().

Stream juga mendefinisikan metode untuk mendapatkan item-item itu. Kami memanggilnya poll_next, untuk jelas bahwa ia mem-poll dengan cara yang sama Future::poll dan menghasilkan urutan item dengan cara yang sama Iterator::next. Tipe kembaliannya menggabungkan Poll dengan Option. Tipe luar adalah Poll, karena ia harus diperiksa kesiapan, sama seperti future. Tipe dalam adalah Option, karena ia perlu menyinyal apakah ada pesan lagi, sama seperti iterator.

Suatu hal yang sangat mirip dengan definisi ini kemungkinan besar akan menjadi bagian dari pustaka standar Rust. Sementara itu, ia bagian dari toolkit kebanyakan runtime, jadi Anda bisa mengandalkannya, dan segala sesuatunya yang kami bahas selanjutnya seharusnya secara umum berlaku!

Di contoh yang kami lihat di bagian “Streams: Futures in Sequence”, bagaimanpun, kami tidak menggunakan poll_next atau Stream, tapi sebagai gantinya menggunakan next dan StreamExt. Kami bisa bekerja langsung dalam hal API poll_next dengan menulis sendiri mesin state Stream, tentu saja, sama seperti kami bisa bekerja dengan future langsung via metode poll mereka. Menggunakan await jauh lebih enak, bagaimanpun, dan trait StreamExt menyediakan metode next sehingga kami bisa melakukan itu:

#![allow(unused)]
fn main() {
use std::pin::Pin;
use std::task::{Context, Poll};

trait Stream {
    type Item;
    fn poll_next(
        self: Pin<&mut Self>,
        cx: &mut Context<'_>,
    ) -> Poll<Option<Self::Item>>;
}

trait StreamExt: Stream {
    async fn next(&mut self) -> Option<Self::Item>
    where
        Self: Unpin;

    // other methods...
}
}

Catatan: Definisi aktual yang kami gunakan sebelumnya di bab ini terlihat sedikit berbeda dari ini, karena ia mendukung versi Rust yang belum mendukung penggunaan fungsi async di trait. Hasilnya, ia terlihat seperti ini:

fn next(&mut self) -> Next<'_, Self> where Self: Unpin;

Tipe Next itu adalah struct yang mengimplementasikan Future dan memungkinkan kami menamai lifetime referensi ke self dengan Next<'_, Self>, sehingga await bisa bekerja dengan metode ini.

Trait StreamExt juga rumah bagi semua metode menarik yang tersedia untuk digunakan dengan stream. StreamExt secara otomatis diimplementasikan untuk setiap tipe yang mengimplementasikan Stream, tapi trait-trait ini didefinisikan terpisah untuk memungkinkan komunitas beriterasi pada convenience APIs tanpa mempengaruhi trait fondasi.

Di versi StreamExt yang digunakan di crate trpl, trait tidak hanya mendefinisikan metode next tapi juga menyediakan implementasi default next yang dengan benar menangani detail memanggil Stream::poll_next. Artinya bahkan saat Anda perlu menulis tipe streaming data sendiri, Anda hanya perlu mengimplementasikan Stream, dan lalu siapa pun yang menggunakan tipe data Anda bisa menggunakan StreamExt dan metodenya secara otomatis.

Itu semua yang akan kami bahas untuk detail lower-level pada trait- trait ini. Untuk menutup, mari pertimbangkan bagaimana future (termasuk stream), task, dan thread semua cocok bersama!
