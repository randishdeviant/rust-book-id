The Rust Programming Language

Refactoring untuk Meningkatkan Modularitas dan Penanganan Kesalahan

Untuk meningkatkan program kami, kami akan memperbaiki empat masalah yang berhubungan dengan struktur program dan cara penanganan kesalahan potensial. Pertama, fungsi main kami sekarang melakukan dua tugas: Ia mem-parsing argumen dan membaca berkas. Seiring program berkembang, jumlah tugas terpisah yang ditangani fungsi main akan bertambah. Seiring fungsi mendapatkan tanggung jawab, ia menjadi lebih sulit untuk dipahami, lebih sulit diuji, dan lebih sulit diubah tanpa merusak salah satu bagiannya. Lebih baik memisahkan fungsionalitas sehingga setiap fungsi bertanggung jawab untuk satu tugas.

Masalah ini juga berkaitan dengan masalah kedua: Meskipun query dan file_path adalah variabel konfigurasi program kami, variabel seperti contents digunakan untuk menjalankan logika program. Semakin panjang main, semakin banyak variabel yang perlu dibawa ke ruang lingkup; semakin banyak variabel di ruang lingkup, semakin sulit melacak tujuan masing-masing. Lebih baik mengelompokkan variabel konfigurasi ke satu struktur untuk menjadikan tujuannya jelas.

Masalah ketiga adalah kami telah menggunakan expect untuk mencetak pesan kesalahan saat membaca berkas gagal, tapi pesan kesalahan hanya mencetak Should have been able to read the file. Membaca berkas bisa gagal dengan banyak cara: Misalnya, berkas bisa hilang, atau kami mungkin tidak punya izin membukanya. Saat ini, terlepas dari situasi, kami akan mencetak pesan kesalahan yang sama untuk semuanya, yang tidak akan memberi pengguna informasi apa pun!

Keempat, kami menggunakan expect untuk menangani kesalahan, dan jika pengguna menjalankan program kami tanpa menentukan argumen yang cukup, mereka akan mendapat kesalahan index out of bounds dari Rust yang tidak jelas menjelaskan masalah. Akan lebih baik jika semua kode penanganan kesalahan ada di satu tempat sehingga pemelihara masa depan hanya punya satu tempat untuk konsultasi kode jika logika penanganan kesalahan perlu diubah. Memiliki semua kode penanganan kesalahan di satu tempat juga akan memastikan bahwa kami mencetak pesan yang bermakna bagi pengguna akhir kami.

Mari atasi keempat masalah ini dengan merefaktorkan proyek kami.

Memisahkan Tanggung Jawab di Proyek Biner

Masalah organisasi alokasi tanggung jawab untuk beberapa tugas ke fungsi main umum di banyak proyek biner. Sebagai akibatnya, banyak programmer Rust merasa berguna untuk memisahkan tanggung jawab terpisah program biner saat fungsi main mulai besar. Proses ini memiliki langkah-langkah berikut:

  • Pisahkan program Anda ke berkas _main.rs_ dan _lib.rs_ dan pindahkan logika program ke _lib.rs_.
  • Selama logika parsing baris perintah kecil, ia bisa tetap di fungsi main.
  • Saat logika parsing baris perintah mulai rumit, ekstrak dari fungsi main ke fungsi atau tipe lain.

Tanggung jawab yang tersisa di fungsi main setelah proses ini seharusnya terbatas pada hal berikut:

  • Memanggil logika parsing baris perintah dengan nilai argumen
  • Menyiapkan konfigurasi lainnya
  • Memanggil fungsi run di _lib.rs_
  • Menangani kesalahan jika run mengembalikan kesalahan

Pola ini tentang memisahkan tanggung jawab: _main.rs_ menangani menjalankan program dan _lib.rs_ menangani semua logika tugas yang dihadapi. Karena Anda tidak bisa menguji fungsi main secara langsung, struktur ini memungkinkan Anda menguji semua logika program dengan memindahkannya keluar dari fungsi main. Kode yang tersisa di fungsi main akan cukup kecil untuk diverifikasi kebenarannya dengan membacanya. Mari perbaiki program kami dengan mengikuti proses ini.

Mengekstrak Argument Parser

Kami akan mengekstrak fungsionalitas untuk mem-parsing argumen ke fungsi yang akan main panggil. Listing 12-5 menunjukkan awal baru fungsi main yang memanggil fungsi baru parse_config, yang akan kami definisikan di _src/main.rs_.

Kami masih mengumpulkan argumen baris perintah ke vektor, tapi alih-alih menetapkan nilai argumen pada indeks 1 ke variabel query dan nilai argumen pada indeks 2 ke variabel file_path di dalam fungsi main, kami meneruskan seluruh vektor ke fungsi parse_config. Fungsi parse_config kemudian memegang logika yang menentukan argumen mana yang pergi ke variabel mana dan meneruskan nilai-nilai kembali ke main. Kami tetap membuat variabel query dan file_path di main, tapi main tidak lagi memiliki tanggung jawab menentukan bagaimana argumen baris perintah dan variabel bersesuaian.

Pengerjaan ulang ini mungkin terlihat berlebihan untuk program kecil kami, tapi kami merefaktorkan dalam langkah-langkah kecil, inkremental. Setelah melakukan perubahan ini, jalankan program lagi untuk memverifikasi bahwa parsing argumen masih berfungsi. Baik untuk memeriksa kemajuan sering, untuk membantu mengidentifikasi penyebab masalah saat terjadi.

Mengelompokkan Nilai Konfigurasi

Kami bisa mengambil langkah kecil lain untuk meningkatkan fungsi parse_config lebih jauh. Saat ini, kami mengembalikan tuple, tapi lalu kami segera memecah tuple itu kembali ke bagian-bagian individual. Ini tanda bahwa mungkin kami belum memiliki abstraksi yang tepat.

Indikator lain yang menunjukkan ada ruang untuk perbaikan adalah bagian config dari parse_config, yang mengimplikasikan bahwa dua nilai yang kami kembalikan terkait dan keduanya bagian dari satu nilai konfigurasi. Kami saat ini tidak menyampaikan arti ini dalam struktur data selain dengan mengelompokkan dua nilai ke tuple; kami akan sebagai gantinya meletakkan dua nilai ke dalam satu struct dan memberi setiap bidang struct nama yang bermakna. Melakukannya akan memudahkan pemelihara masa depan kode ini memahami bagaimana nilai-nilai berbeda berhubungan satu sama lain dan apa tujuannya.

Listing 12-6 menunjukkan perbaikan ke fungsi parse_config.

Kami telah menambahkan struct bernama Config yang didefinisikan memiliki bidang bernama query dan file_path. Tanda tangan parse_config kini menunjukkan bahwa ia mengembalikan nilai Config. Di badan parse_config, di mana kami dulu mengembalikan slice string yang mereferensikan nilai String di args, kami kini mendefinisikan Config untuk berisi nilai String yang owned. Variabel args di main adalah pemilik nilai argumen dan hanya membiarkan fungsi parse_config meminjamnya, yang berarti kami akan melanggar aturan peminjaman Rust jika Config mencoba mengambil kepemilikan nilai di args.

Ada sejumlah cara kami bisa mengelola data String; rute termudah, meskipun agak tidak efisien, adalah memanggil metode clone pada nilai-nilai. Ini akan membuat salinan penuh data untuk instance Config memiliki, yang memakan lebih banyak waktu dan memori dari menyimpan referensi ke data string. Akan tetapi, meng-clone data juga membuat kode kami sangat langsung karena kami tidak perlu mengelola lifetime referensi; dalam keadaan ini, mengorbankan sedikit performa untuk mendapatkan kesederhanaan adalah trade-off yang layak.

Trade-Off Menggunakan clone

Ada kecenderungan di antara banyak Rustacean untuk menghindari menggunakan clone untuk memperbaiki masalah kepemilikan karena biaya runtime-nya. Di Bab 13, Anda akan belajar cara menggunakan metode lebih efisien dalam situasi tipe ini. Tapi untuk sekarang, tidak apa-apa menyalin beberapa string untuk terus membuat kemajuan karena Anda hanya akan membuat salinan ini sekali dan jalur berkas dan string query Anda sangat kecil. Lebih baik memiliki program yang bekerja tapi agak tidak efisien daripada mencoba mengoptimalkan kode secara berlebihan pada lolos pertama. Seiring Anda menjadi lebih berpengalaman dengan Rust, akan lebih mudah memulai dengan solusi paling efisien, tapi untuk sekarang, sangat boleh memanggil clone.

Kami telah memperbarui main sehingga ia meletakkan instance Config yang dikembalikan oleh parse_config ke variabel bernama config, dan kami memperbarui kode yang sebelumnya menggunakan variabel query dan file_path terpisah sehingga kini menggunakan bidang pada struct Config aslinya.

Sekarang kode kami dengan lebih jelas menyampaikan bahwa query dan file_path terkait dan bahwa tujuan mereka adalah mengonfigurasi cara program akan bekerja. Kode apa pun yang menggunakan nilai-nilai ini tahu untuk menemukannya di instance config di bidang yang dinamai untuk tujuan mereka.

Memanggil Config::build dan Menangani Kesalahan

Untuk menangani kasus kesalahan dan mencetak pesan ramah pengguna, kami perlu memperbarui main untuk menangani Result yang dikembalikan oleh Config::build, seperti yang ditampilkan di Listing 12-10. Kami juga akan mengambil tanggung jawab keluar dari alat baris perintah dengan kode kesalahan non-nol dari panic! dan sebagai gantinya mengimplementasikannya secara manual. Status keluar non-nol adalah konvensi untuk memberi sinyal ke proses yang memanggil program kami bahwa program keluar dengan state kesalahan.

Di listing ini, kami telah menggunakan metode yang belum kami bahas detail: unwrap_or_else, yang didefinisikan pada Result<T, E> oleh pustaka standar. Menggunakan unwrap_or_else memungkinkan kami mendefinisikan penanganan kesalahan kustom, non-panic!. Jika Result adalah nilai Ok, perilaku metode ini mirip unwrap: Ia mengembalikan nilai dalam yang dibungkus Ok. Akan tetapi, jika nilainya adalah Err, metode ini memanggil kode di closure, yang adalah fungsi anonim yang kami definisikan dan teruskan sebagai argumen ke unwrap_or_else. Kami akan membahas closure lebih detail di Bab 13. Untuk sekarang, Anda hanya perlu tahu bahwa unwrap_or_else akan meneruskan nilai dalam Err, yang dalam kasus ini adalah string statis "not enough arguments" yang kami tambah di Listing 12-9, ke closure kami di argumen err yang muncul di antara pipa vertikal. Kode di closure kemudian bisa menggunakan nilai err saat dijalankan.

Kami telah menambahkan baris use baru untuk membawa process dari pustaka standar ke ruang lingkup. Kode di closure yang akan dijalankan di kasus kesalahan hanya dua baris: Kami mencetak nilai err dan lalu memanggil process::exit. Fungsi process::exit akan menghentikan program segera dan mengembalikan angka yang diteruskan sebagai kode status keluar. Ini mirip dengan penanganan berbasis panic! yang kami gunakan di Listing 12-8, tapi kami tidak lagi mendapat semua output tambahan. Mari coba:

Mengembalikan Kesalahan dari run

Dengan logika program yang tersisa dipisahkan ke fungsi run, kami bisa meningkatkan penanganan kesalahan, seperti yang kami lakukan dengan Config::build di Listing 12-9. Alih-alih mengizinkan program panic dengan memanggil expect, fungsi run akan mengembalikan Result<T, E> saat sesuatu yang salah. Ini akan memungkinkan kami lebih lanjut mengonsolidasikan logika di sekitar penanganan kesalahan ke main dengan cara ramah pengguna. Listing 12-12 menunjukkan perubahan yang perlu kami buat ke tanda tangan dan badan run.

Kami telah membuat tiga perubahan signifikan di sini. Pertama, kami mengubah tipe kembalian fungsi run menjadi Result<(), Box<dyn Error>>. Fungsi ini sebelumnya mengembalikan tipe unit, (), dan kami mempertahankannya sebagai nilai yang dikembalikan di kasus Ok.

Untuk tipe kesalahan, kami menggunakan trait object Box<dyn Error> (dan kami membawa std::error::Error ke ruang lingkup dengan pernyataan use di bagian atas). Kami akan membahas trait object di Bab 18. Untuk sekarang, cukup tahu bahwa Box<dyn Error> berarti fungsi akan mengembalikan tipe yang mengimplementasikan trait Error, tapi kami tidak perlu menentukan tipe khusus apa nilai kembalian akan menjadi. Ini memberi kami fleksibilitas untuk mengembalikan nilai kesalahan yang mungkin bertipe berbeda di kasus kesalahan berbeda. Kata kunci dyn adalah singkatan dari dynamic.

Kedua, kami telah menghapus pemanggilan expect demi operator ?, seperti yang kami bahas di Bab 9. Alih-alih panic! pada kesalahan, ? akan mengembalikan nilai kesalahan dari fungsi saat ini untuk pemanggil yang akan menanganinya.

Ketiga, fungsi run kini mengembalikan nilai Ok di kasus sukses. Kami telah mendeklarasikan tipe sukses fungsi run sebagai () di tanda tangan, yang berarti kami perlu membungkus tipe unit dalam nilai Ok. Sintaks Ok(()) ini mungkin terlihat agak aneh pada awalnya. Tapi menggunakan () seperti ini adalah cara idiomatik untuk menandakan bahwa kami memanggil run untuk side effect-nya saja; ia tidak mengembalikan nilai yang kami butuhkan.

Menangani Kesalahan yang Dikembalikan run di main

Kami akan memeriksa kesalahan dan menanganinya menggunakan teknik mirip yang kami gunakan dengan Config::build di Listing 12-10, tapi dengan perbedaan kecil:

Nama Berkas: src/main.rs

use std::env;
use std::error::Error;
use std::fs;
use std::process;

fn main() {
    // --snip--

    let args: Vec<String> = env::args().collect();

    let config = Config::build(&args).unwrap_or_else(|err| {
        println!("Problem parsing arguments: {err}");
        process::exit(1);
    });

    println!("Searching for {}", config.query);
    println!("In file {}", config.file_path);

    if let Err(e) = run(config) {
        println!("Application error: {e}");
        process::exit(1);
    }
}

fn run(config: Config) -> Result<(), Box<dyn Error>> {
    let contents = fs::read_to_string(config.file_path)?;

    println!("With text:\n{contents}");

    Ok(())
}

struct Config {
    query: String,
    file_path: String,
}

impl Config {
    fn build(args: &[String]) -> Result<Config, &'static str> {
        if args.len() < 3 {
            return Err("not enough arguments");
        }

        let query = args[1].clone();
        let file_path = args[2].clone();

        Ok(Config { query, file_path })
    }
}

Kami menggunakan if let bukannya unwrap_or_else untuk memeriksa apakah run mengembalikan nilai Err dan memanggil process::exit(1) jika ya. Fungsi run tidak mengembalikan nilai yang kami ingin unwrap dengan cara yang sama seperti Config::build mengembalikan instance Config. Karena run mengembalikan () di kasus sukses, kami hanya peduli mendeteksi kesalahan, jadi kami tidak butuh unwrap_or_else untuk mengembalikan nilai tanpa bungkus, yang hanya akan menjadi ().

Badan fungsi if let dan unwrap_or_else sama di kedua kasus: Kami mencetak kesalahan dan keluar.

Memecah Kode ke Library Crate

Proyek minigrep kami terlihat bagus sejauh ini! Sekarang kami akan memecah berkas _src/main.rs_ dan menaruh beberapa kode ke berkas _src/lib.rs_. Dengan begitu, kami bisa menguji kode dan memiliki berkas _src/main.rs_ dengan tanggung jawab lebih sedikit.

Mari definisikan kode yang bertanggung jawab untuk mencari teks di _src/lib.rs_ bukannya di _src/main.rs_, yang akan memungkinkan kami (atau siapa pun yang menggunakan library minigrep kami) memanggil fungsi pencarian dari konteks lebih banyak dari biner minigrep kami.

Pertama, mari definisikan tanda tangan fungsi search di _src/lib.rs_ seperti yang ditampilkan di Listing 12-13, dengan badan yang memanggil makro unimplemented!. Kami akan menjelaskan tanda tangan lebih detail saat kami mengisi implementasinya.

Kami telah menggunakan kata kunci pub pada definisi fungsi untuk menunjuk search sebagai bagian dari API publik crate library kami. Kami kini memiliki crate library yang bisa kami gunakan dari crate biner kami dan yang bisa kami uji!

Sekarang kami perlu membawa kode yang didefinisikan di _src/lib.rs_ ke dalam ruang lingkup crate biner di _src/main.rs_ dan memanggilnya, seperti yang ditampilkan di Listing 12-14.

Kami menambahkan baris use minigrep::search untuk membawa fungsi search dari crate library ke ruang lingkup crate biner. Lalu, di fungsi run, alih-alih mencetak isi berkas, kami memanggil fungsi search dan meneruskan nilai config.query dan contents sebagai argumen. Lalu, run akan menggunakan loop for untuk mencetak setiap baris yang dikembalikan dari search yang cocok dengan query. Ini juga waktu yang baik untuk menghapus pemanggilan println! di fungsi main yang menampilkan query dan jalur berkas sehingga program kami hanya mencetak hasil pencarian (jika tidak ada kesalahan terjadi).

Perhatikan bahwa fungsi pencarian akan mengumpulkan semua hasil ke vektor yang ia kembalikan sebelum pencetakan terjadi. Implementasi ini bisa lambat menampilkan hasil saat mencari berkas besar, karena hasil tidak dicetak saat ditemukan; kami akan membahas cara mungkin memperbaiki ini menggunakan iterator di Bab 13.

Phew! Itu banyak pekerjaan, tapi kami telah menyiapkan kami untuk sukses di masa depan. Sekarang jauh lebih mudah menangani kesalahan, dan kami telah membuat kode lebih modular. Hampir semua pekerjaan kami akan dilakukan di _src/lib.rs_ mulai sekarang.

Mari manfaatkan modularitas baru ini dengan melakukan sesuatu yang sulit dengan kode lama tapi mudah dengan kode baru: Kami akan menulis beberapa pengujian!
