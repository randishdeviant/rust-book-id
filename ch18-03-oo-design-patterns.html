The Rust Programming Language

Mengimplementasikan Pola Desain Berorientasi Objek

Pola state adalah pola desain berorientasi objek. Inti dari pola ini adalah kita mendefinisikan sekumpulan state yang bisa dimiliki suatu nilai secara internal. State-state itu diwakili oleh sekumpulan state objects, dan perilaku nilai berubah berdasarkan state-nya. Kami akan bekerja melalui contoh struct blog post yang punya field untuk menampung state-nya, yang akan menjadi state object dari kumpulan “draft,” “review,” atau “published.”

State objects berbagi fungsionalitas: Di Rust, tentu saja, kami menggunakan struct dan trait alih-alih objek dan pewarisan. Setiap state object bertanggung jawab atas perilakunya sendiri dan mengatur kapan harus berubah ke state lain. Nilai yang menampung state object tidak tahu apa pun tentang perilaku berbeda dari state-state atau kapan transisi antar state.

Kelebihan menggunakan state pattern adalah bahwa, saat persyaratan bisnis program berubah, kami tidak perlu mengubah kode nilai yang menampung state atau kode yang menggunakan nilai itu. Kami hanya perlu memperbarui kode di dalam salah satu state object untuk mengubah atasurannya atau mungkin menambah state object lagi.

Pertama, kami akan mengimplementasikan state pattern dengan cara object-oriented tradisional. Lalu, kami akan menggunakan pendekatan yang sedikit lebih natural di Rust. Mari selami untuk mengimplementasikan alur kerja blog post secara inkremental menggunakan state pattern.

Fungsionalitas final akan terlihat seperti ini:

  1. Sebuah blog post dimulai sebagai draft kosong.
  2. Saat draft selesai, review post diminta.
  3. Saat post disetujui, ia dipublikasikan.
  4. Hanya blog post yang dipublikasikan yang mengembalikan konten untuk dicetak sehingga post yang belum disetujui tidak bisa tidak sengaja dipublikasikan.

Perubahan lain yang dicoba pada post seharusnya tidak berpengaruh. Misalnya, jika kita mencoba menyetujui draft blog post sebelum kita meminta review, post harus tetap menjadi draft tidak dipublikasikan.

Mencoba Gaya Object-Oriented Tradisional

Ada tak terhingga cara struktur kode untuk memecahkan masalah yang sama, masing-masing dengan trade-off berbeda. Implementasi bagian ini adalah lebih gaya object-oriented tradisional, yang memungkinkan ditulis di Rust, tapi tidak memanfaatkan beberapa kekuatan Rust. Nanti, kami akan mendemonstrasikan solusi berbeda yang tetap menggunakan pola desain object-oriented tapi terstruktur dengan cara yang mungkin terlihat kurang familiar bagi programmer dengan pengalaman object-oriented. Kami akan membandingkan kedua solusi untuk merasakan trade-off mendesain kode Rust berbeda dari kode di bahasa lain.

Listing 18-11 menunjukkan alur kerja ini dalam bentuk kode: Ini contoh penggunaan API yang akan kami implementasikan di library crate bernama blog. Ini belum akan kompilasi karena kami belum mengimplementasikan crate blog.

Kami ingin mengizinkan pengguna membuat draft blog post baru dengan Post::new. Kami ingin mengizinkan teks ditambahkan ke blog post. Jika kita mencoba mendapatkan konten post segera, sebelum approval, kita tidak seharusnya mendapat teks apa pun karena post masih draft. Kami telah menambahkan assert_eq! di kode untuk tujuan demonstrasi. Unit test yang bagus untuk ini akan menegaskan bahwa draft blog post mengembalikan string kosong dari metode content, tapi kami tidak akan menulis test untuk contoh ini.

Selanjutnya, kami ingin mengaktifkan permintaan review post, dan menginginkan content mengembalikan string kosong saat menunggu review. Saat post mendapat approval, ia seharusnya dipublikasikan, artinya teks post akan dikembalikan saat content dipanggil.

Perhatikan bahwa satu-satunya tipe yang kami interaksikan dari crate adalah tipe Post. Tipe ini akan menggunakan state pattern dan menampung nilai yang akan menjadi salah satu dari tiga state object yang mewakili berbagai state post bisa berada—draft, review, atau published. Perubahan dari satu state ke state lain akan dikelola secara internal di dalam tipe Post. State berubah sebagai respons metode yang dipanggil oleh pengguna library kami pada instance Post, tapi mereka tidak perlu mengelola perubahan state secara langsung. Juga, pengguna tidak bisa membuat kesalahan dengan state, seperti publikasi post sebelum direview.

Mendefinisikan Post dan Membuat Instance Baru

Mari mulai implementasi library! Kami tahu kami butuh struct Post publik yang menampung beberapa konten, jadi kami akan mulai dengan definisi struct dan associated public function new untuk membuat instance Post, seperti yang ditampilkan di Listing 18-12. Kami juga akan membuat trait State privat yang akan mendefinisikan perilaku yang harus dimiliki semua state object untuk Post.

Lalu, Post akan menampung trait object Box<dyn State> di dalam Option<T> di field privat bernama state untuk menampung state object. Anda akan melihat mengapa Option<T> diperlukan sebentar lagi.

Trait State mendefinisikan perilaku yang dibagi oleh state post yang berbeda. State objects adalah Draft, PendingReview, dan Published, dan mereka semua akan mengimplementasikan trait State. Untuk saat ini, trait tidak punya metode apa pun, dan kami akan mulai dengan mendefinisikan hanya state Draft karena itulah state di mana post dimulai.

Saat kami membuat Post baru, kami set field state-nya ke nilai Some yang menampung Box. Box ini menunjuk ke instance baru struct Draft. Ini memastikan bahwa kapan pun kami membuat instance baru Post, ia akan mulai sebagai draft. Karena field state dari Post privat, tidak ada cara membuat Post di state lain! Di fungsi Post::new, kami set field content ke String baru, kosong.

Menyimpan Teks Konten Post

Kami melihat di Listing 18-11 bahwa kami ingin bisa memanggil metode bernama add_text dan meneruskan &str yang kemudian ditambahkan sebagai teks konten blog post. Kami mengimplementasikan ini sebagai metode, alih-alih mengekspos field content sebagai pub, sehingga nanti kami bisa mengimplementasikan metode yang akan mengontrol bagaimana data field content dibaca. Metode add_text cukup straightforward, jadi mari tambahkan implementasi di Listing 18-13 ke blok impl Post.

Metode add_text mengambil mutable reference ke self karena kami mengubah instance Post yang kami panggil add_text padanya. Kami kemudian memanggil push_str pada String di content dan meneruskan argumen text untuk ditambahkan ke content yang disimpan. Perilaku ini tidak bergantung pada state post, jadi bukan bagian dari state pattern. Metode add_text tidak berinteraksi dengan field state sama sekali, tapi itu bagian dari perilaku yang ingin kami dukung.

Memastikan Konten Draft Post Kosong

Meski setelah kami memanggil add_text dan menambah konten ke post kami, kami tetap ingin metode content mengembalikan slice string kosong karena post masih dalam state draft, seperti yang ditunjukkan oleh assert_eq! pertama di Listing 18-11. Untuk saat ini, mari implementasikan metode content dengan hal paling sederhana yang memenuhi persyaratan ini: selalu mengembalikan slice string kosong. Kami akan mengubah ini nanti setelah kami mengimplementasikan kemampuan mengubah state post sehingga bisa dipublikasikan. Sejauh ini, post hanya bisa dalam state draft, jadi konten post seharusnya selalu kosong. Listing 18-14 menunjukkan implementasi placeholder ini.

Dengan metode content yang ditambah ini, semuanya di Listing 18-11 sampai assert_eq! pertama bekerja seperti yang diinginkan.

Meminta Review, Yang Mengubah State Post

Selanjutnya, kami perlu menambah fungsionalitas untuk meminta review post, yang seharusnya mengubah state-nya dari Draft ke PendingReview. Listing 18-15 menunjukkan kode ini.

Kami memberi Post metode publik bernama request_review yang akan mengambil mutable reference ke self. Lalu, kami memanggil internal method request_review pada state saat ini Post, dan method request_review kedua ini mengkonsumsi state saat ini dan mengembalikan state baru.

Kami menambahkan metode request_review ke trait State; semua tipe yang mengimplementasikan trait sekarang perlu mengimplementasikan metode request_review. Perhatikan bahwa alih-alih punya self, &self, atau &mut self sebagai parameter pertama metode, kami punya self: Box<Self>. Sintaks ini berarti metode hanya valid saat dipanggil pada Box yang menampung tipe. Sintaks ini mengambil kepemilikan Box<Self>, meng-invalid-kan state lama sehingga nilai state Post bisa transform ke state baru.

Untuk mengkonsumsi state lama, metode request_review perlu mengambil kepemilikan nilai state. Di sinilah Option di field state dari Post berguna: Kami memanggil metode take untuk mengambil nilai Some keluar dari field state dan meninggalkan None di tempatnya karena Rust tidak mengizinkan field struct yang tidak terisi. Ini memungkinkan kami memindahkan nilai state keluar dari Post alih-alih meminjamnya. Lalu, kami akan set nilai state post ke hasil operasi ini.

Kami perlu set state ke None sementara alih-alih set langsung dengan kode seperti self.state = self.state.request_review(); untuk mendapatkan kepemilikan nilai state. Ini memastikan Post tidak bisa menggunakan nilai state lama setelah kami mentransformasikannya ke state baru.

Metode request_review pada Draft mengembalikan instance baru, boxed, dari struct PendingReview baru, yang mewakili state saat post menunggu review. Struct PendingReview juga mengimplementasikan metode request_review tapi tidak melakukan transformasi apa pun. Sebagai gantinya, ia mengembalikan dirinya sendiri karena saat kami meminta review pada post yang sudah di state PendingReview, ia seharusnya tetap di state PendingReview.

Sekarang kami mulai melihat keuntungan state pattern: Metode request_review pada Post sama apa pun nilai state-nya. Masing- masing state bertanggung jawab atas aturannya sendiri.

Kami akan biarkan metode content pada Post apa adanya, mengembalikan slice string kosong. Kami sekarang bisa punya Post di state PendingReview serta di state Draft, tapi kami ingin perilaku sama di state PendingReview. Listing 18-11 sekarang bekerja sampai pemanggilan assert_eq! kedua!

Menambah approve untuk Mengubah Perilaku content

Metode approve akan mirip dengan metode request_review: Ia akan set state ke nilai yang dikatakan state saat ini seharusnya punya saat state itu disetujui, seperti yang ditampilkan di Listing 18-16.

Kami menambahkan metode approve ke trait State dan menambah struct baru yang mengimplementasikan State, state Published.

Mirip dengan cara request_review pada PendingReview bekerja, jika kami memanggil metode approve pada Draft, ia tidak akan berpengaruh karena approve akan mengembalikan self. Saat kami memanggil approve pada PendingReview, ia mengembalikan instance baru, boxed, dari struct Published. Struct Published mengimplementasikan trait State, dan untuk kedua metode request_review dan approve, ia mengembalikan dirinya sendiri karena post harus tetap di state Published di kasus-kasus itu.

Sekarang kami perlu memperbarui metode content pada Post. Kami ingin nilai yang dikembalikan dari content bergantung pada state saat ini Post, jadi kami akan membuat Post mendelegasikan ke metode content yang didefinisikan pada state-nya, seperti yang ditampilkan di Listing 18-17.

Karena tujuannya adalah menjaga semua aturan ini di dalam struct yang mengimplementasikan State, kami memanggil metode content pada nilai di state dan meneruskan instance post (yaitu, self) sebagai argumen. Lalu, kami mengembalikan nilai yang dikembalikan dari menggunakan metode content pada nilai state.

Kami memanggil metode as_ref pada Option karena kami ingin referensi ke nilai di dalam Option alih-alih kepemilikan nilai. Karena state adalah Option<Box<dyn State>>, saat kami memanggil as_ref, Option<&Box<dyn State>> dikembalikan. Jika kami tidak memanggil as_ref, kami akan mendapat error karena kami tidak bisa memindahkan state keluar dari &self yang dipinjam parameter fungsi.

Kami lalu memanggil metode unwrap, yang kami tahu tidak akan pernah panic karena kami tahu metode-metode pada Post memastikan state selalu berisi nilai Some saat metode-metode itu selesai. Ini salah satu kasus yang kami bicarakan di bagian “Ketika Anda Memiliki Informasi Lebih dari Compiler” di Bab 9 saat kami tahu bahwa nilai None tidak mungkin, meski compiler tidak mampu memahaminya.

Pada titik ini, saat kami memanggil content pada &Box<dyn State>, deref coercion akan berlaku pada & dan Box sehingga metode content akhirnya akan dipanggil pada tipe yang mengimplementasikan trait State. Artinya kami perlu menambahkan content ke definisi trait State, dan di sinilah kami akan menaruh logika untuk konten apa yang dikembalikan tergantung state mana yang kami miliki, seperti yang ditampilkan di Listing 18-18.

Kami menambahkan implementasi default untuk metode content yang mengembalikan slice string kosong. Artinya kami tidak perlu mengimplementasikan content pada struct Draft dan PendingReview. Struct Published akan meng-override metode content dan mengembalikan nilai di post.content. Meski nyata, memiliki metode content pada State yang menentukan konten Post adalah mengaburkan garis antara tanggung jawab State dan tanggung jawab Post.

Perhatikan bahwa kami butuh anotasi lifetime pada metode ini, seperti yang dibahas di Bab 10. Kami mengambil referensi ke post sebagai argumen dan mengembalikan referensi ke bagian dari post itu, jadi lifetime referensi yang dikembalikan terkait dengan lifetime argumen post.

Dan selesai—semua Listing 18-11 sekarang berfungsi! Kami telah mengimplementasikan state pattern dengan aturan alur kerja blog post. Logika terkait aturan tinggal di state object alih-alih tersebar di seluruh Post.

Mengapa Bukan Enum?

Anda mungkin bertanya-tanya mengapa kami tidak menggunakan enum dengan varian state post yang berbeda sebagai varian. Itu pasti solusi yang mungkin; coba dan bandingkan hasil akhir untuk melihat mana yang Anda sukai! Satu kelemahan menggunakan enum adalah setiap tempat yang memeriksa nilai enum akan butuh ekspresi match atau serupa untuk menangani setiap varian yang mungkin. Ini bisa jadi lebih repetitif dari solusi trait object ini.

Mengevaluasi State Pattern

Kami telah menunjukkan bahwa Rust mampu mengimplementasikan pola state object-oriented untuk mengenkapsulasi berbagai jenis perilaku yang seharusnya dimiliki post di setiap state. Metode pada Post tidak tahu apa pun tentang perilaku berbagai. Karena cara kami mengorganisir kode, kami hanya perlu melihat di satu tempat untuk mengetahui berbagai cara published post bisa berperilaku: implementasi trait State pada struct Published.

Jika kami membuat implementasi alternatif yang tidak menggunakan state pattern, kami mungkin akan menggunakan ekspresi match di metode pada Post atau bahkan di kode main yang memeriksa state post dan mengubah perilaku di tempat-tempat itu. Artinya kami harus melihat di beberapa tempat untuk memahami semua implikasi post berada di state published.

Dengan state pattern, metode Post dan tempat-tempat kami menggunakan Post tidak butuh ekspresi match, dan untuk menambah state baru, kami hanya perlu menambah struct baru dan mengimplementasikan metode trait pada struct tunggal itu di satu lokasi.

Implementasi menggunakan state pattern mudah diperluas untuk menambah fungsionalitas lebih. Untuk melihat kesederhanaan memelihara kode yang menggunakan state pattern, coba beberapa saran ini:

  • Tambah metode reject yang mengubah state post dari PendingReview kembali ke Draft.
  • Butuh dua pemanggilan approve sebelum state bisa diubah ke Published.
  • Izinkan pengguna menambah konten teks hanya saat post di state Draft. Petunjuk: biarkan state object yang bertanggung jawab atas apa yang mungkin berubah tentang konten tapi tidak bertanggung jawab memodifikasi Post.

Satu kelemahan state pattern adalah bahwa, karena state mengimplementasikan transisi antar state, beberapa state terikat (coupled) satu sama lain. Jika kami menambah state lain di antara PendingReview dan Published, seperti Scheduled, kami harus mengubah kode di PendingReview untuk transisi ke Scheduled sebagai gantinya. Akan lebih sedikit kerja jika PendingReview tidak perlu berubah dengan penambahan state baru, tapi itu berarti beralih ke pola desain lain.

Kelemahan lain adalah kami menduplikasi beberapa logika. Untuk menghilangkan beberapa duplikasi, kami mungkin coba membuat implementasi default untuk metode request_review dan approve pada trait State yang mengembalikan self. Akan tetapi, ini tidak akan bekerja: Saat menggunakan State sebagai trait object, trait tidak tahu self konkret apa persisnya, jadi tipe pengembalian tidak dikenal pada waktu kompilasi. (Ini salah satu aturan dyn compatibility yang disebutkan sebelumnya.)

Duplikasi lain mencakup implementasi serupa dari metode request_review dan approve pada Post. Kedua metode menggunakan Option::take dengan field state dari Post, dan jika state adalah Some, mereka mendelegasikan ke implementasi nilai yang dibungkus dari metode yang sama dan menetapkan nilai baru field state ke hasilnya. Jika kami punya banyak metode pada Post yang mengikuti pola ini, kami mungkin mempertimbangkan mendefinisikan makro untuk menghilangkan pengulangan (lihat bagian “Makro” di Bab 20).

Dengan mengimplementasikan state pattern persis seperti yang didefinisikan untuk bahasa object-oriented, kami tidak mengambil sepenuhnya keuntungan kekuatan Rust sebagus yang bisa. Mari lihat beberapa perubahan yang bisa kami buat ke crate blog yang bisa membuat state dan transisi invalid menjadi error pada waktu kompilasi.

Mengenkode State dan Perilaku sebagai Tipe

Kami akan menunjukkan cara memikir ulang state pattern untuk mendapatkan set trade-off berbeda. Alih-alih mengenkapsulasi state dan transisi sepenuhnya sehingga kode luar tidak punya pengetahuan tentang mereka, kami akan mengenkode state ke tipe yang berbeda. Akibatnya, sistem type-checking Rust akan mencegah upaya menggunakan draft post di mana hanya published post yang diizinkan dengan mengeluarkan error compiler.

Mari pertimbangkan bagian pertama main di Listing 18-11:

Kami tetap mengaktifkan pembuatan post baru di state draft menggunakan Post::new dan kemampuan menambah teks ke konten post. Tapi alih-alih punya metode content pada draft post yang mengembalikan string kosong, kami akan membuatnya sehingga draft post tidak punya metode content sama sekali. Dengan begitu, jika kami mencoba mendapatkan konten draft post, kami akan mendapat error compiler yang bilang metode tidak ada. Hasilnya, tidak mungkin bagi kami untuk secara tidak sengaja menampilkan konten draft post di production karena kode itu bahkan tidak akan kompilasi. Listing 18-19 menunjukkan definisi struct Post dan struct DraftPost, serta metode pada masing-masing.

Kedua struct Post dan DraftPost punya field content privat yang menyimpan teks blog post. Struct-struct tidak lagi punya field state karena kami memindahkan pengkodean state ke tipe struct-struct. Struct Post akan mewakili post yang dipublikasikan, dan ia punya metode content yang mengembalikan content.

Kami tetap punya fungsi Post::new, tapi alih-alih mengembalikan instance Post, ia mengembalikan instance DraftPost. Karena content privat dan tidak ada fungsi yang mengembalikan Post, tidak mungkin membuat instance Post sekarang.

Struct DraftPost punya metode add_text, jadi kami bisa menambah teks ke content seperti sebelumnya, tapi perhatikan bahwa DraftPost tidak punya metode content terdefinisi! Jadi sekarang program memastikan semua post dimulai sebagai draft post, dan draft post tidak punya kontennya tersedia untuk ditampilkan. Upaya apa pun untuk mengelak batasan ini akan menghasilkan error compiler.

Jadi, bagaimana cara mendapatkan published post? Kami ingin menegakkan aturan bahwa draft post harus direview dan disetujui sebelum bisa dipublikasikan. Post di state pending review seharusnya tetap tidak menampilkan konten. Mari implementasikan batasan ini dengan menambah struct lain, PendingReviewPost, mendefinisikan metode request_review pada DraftPost untuk mengembalikan PendingReviewPost dan mendefinisikan metode approve pada PendingReviewPost untuk mengembalikan Post, seperti yang ditampilkan di Listing 18-20.

Metode request_review dan approve mengambil kepemilikan self, dengan demikian mengkonsumsi instance DraftPost dan PendingReviewPost dan mentransformasikannya menjadi PendingReviewPost dan Post yang dipublikasikan, secara berurutan. Dengan cara ini, kami tidak akan punya instance DraftPost yang tersisa setelah kami memanggil request_review pada mereka, dan seterusnya. Struct PendingReviewPost tidak punya metode content terdefinisi padanya, jadi upaya membaca kontennya menghasilkan error compiler, seperti pada DraftPost. Karena satu-satunya cara mendapat instance Post yang dipublikasikan yang memang punya metode content terdefinisi adalah dengan memanggil metode approve pada PendingReviewPost, dan satu-satunya cara mendapat PendingReviewPost adalah dengan memanggil metode request_review pada DraftPost, kami sekarang telah mengenkode alur kerja blog post ke dalam sistem tipe.

Tapi kami juga harus membuat beberapa perubahan kecil ke main. Metode request_review dan approve mengembalikan instance baru alih-alih memodifikasi struct yang mereka dipanggil, jadi kami perlu menambah lebih banyak assignment let post = shadowing untuk menyimpan instance yang dikembalikan. Kami juga tidak bisa punya asersi tentang konten draft dan pending review posts menjadi string kosong, dan kami tidak butuh mereka: Kami tidak bisa mengompilasi kode yang mencoba menggunakan konten post di state-state tersebut lagi. Kode main yang diupdate ditampilkan di Listing 18-21.

Perubahan yang kami butuhkan ke main untuk reassign post berarti implementasi ini tidak lagi mengikuti object-oriented state pattern dengan ketat: Transformasi antar state tidak lagi dienkapsulasi sepenuhnya di dalam implementasi Post. Akan tetapi, keuntungan kami adalah state invalid sekarang tidak mungkin karena sistem tipe dan type checking yang terjadi pada waktu kompilasi! Ini memastikan bahwa bug tertentu, seperti penampilan konten post yang belum dipublikasikan, akan ditemukan sebelum sampai ke production.

Coba tugas-tugas yang disarankan di awal bagian ini pada crate blog sebagaimana setelah Listing 18-21 untuk melihat apa pendapat Anda tentang desain versi kode ini. Perhatikan bahwa beberapa tugas mungkin sudah selesai di desain ini.

Kami telah melihat bahwa meski Rust mampu mengimplementasikan pola desain object-oriented, pola lain, seperti mengenkode state ke dalam sistem tipe, juga tersedia di Rust. Pola-pola ini punya trade-off yang berbeda. Meski Anda mungkin sangat familiar dengan pola object-oriented, memikirkan ulang masalah untuk memanfaatkan fitur Rust bisa memberikan manfaat, seperti mencegah beberapa bug pada waktu kompilasi. Pola object-oriented tidak selalu menjadi solusi terbaik di Rust karena fitur tertentu, seperti ownership, yang tidak dimiliki bahasa object-oriented.

Ringkasan

Terlepas dari apakah Anda menganggap Rust sebagai bahasa object-oriented setelah membaca bab ini, Anda sekarang tahu bahwa Anda bisa menggunakan trait objects untuk mendapatkan beberapa fitur object-oriented di Rust. Dynamic dispatch bisa memberi kode Anda fleksibilitas beberapa sebagai tukar menukar sedikit performa runtime. Anda bisa menggunakan fleksibilitas ini untuk mengimplementasikan pola object-oriented yang bisa membantu maintainability kode Anda. Rust juga punya fitur lain, seperti ownership, yang tidak dimiliki bahasa object-oriented. Pola object-oriented tidak selalu akan menjadi cara terbaik memanfaatkan kekuatan Rust, tapi itu opsi yang tersedia.

Selanjutnya, kami akan melihat pola (patterns), yang lain dari fitur Rust yang mengaktifkan banyak fleksibilitas. Kami telah melihatnya secara singkat sepanjang buku tapi belum melihat kemampuan penuhnya lagi. Ayo lanjut!
