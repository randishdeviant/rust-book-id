The Rust Programming Language

Membangun Web Server Single-Threaded

Kami akan memulai dengan membuat web server single-threaded yang bekerja. Sebelum memulai, mari lihat gambaran singkat protokol yang terlibat dalam membangun web server. Detail protokol ini di luar cakupan buku ini, tapi gambaran singkat akan memberi Anda informasi yang Anda butuhkan.

Dua protokol utama yang terlibat di web server adalah Hypertext Transfer Protocol (HTTP) dan Transmission Control Protocol (TCP). Kedua protokol ini adalah protokol request-response, artinya seorang client memulai permintaan dan sebuah server mendengarkan permintaan dan menyediakan respons ke client. Isi dari permintaan dan respons tersebut didefinisikan oleh protokol.

TCP adalah protokol level-lower yang mendeskripsikan detail bagaimana informasi sampai dari satu server ke server lain tapi tidak menspesifikasikan informasi apa itu. HTTP membangun di atas TCP dengan mendefinisikan isi permintaan dan respons. Secara teknis memungkinkan menggunakan HTTP dengan protokol lain, tapi di sebagian besar kasus, HTTP mengirim datanya melalui TCP. Kami akan bekerja dengan byte mentah dari permintaan dan respons TCP dan HTTP.

Mendengarkan Koneksi TCP

Web server kami perlu mendengarkan koneksi TCP, jadi itulah bagian pertama yang akan kami kerjakan. Pustaka standar menawarkan modul std::net yang memungkinkan kami melakukan ini. Mari buat proyek baru dengan cara biasa:

$ cargo new hello
     Created binary (application) `hello` project
$ cd hello

Sekarang masukkan kode di Listing 21-1 di src/main.rs untuk memulai. Kode ini akan mendengarkan di alamat lokal 127.0.0.1:7878 untuk stream TCP masuk. Saat mendapat stream masuk, ia akan mencetak Connection established!.

Menggunakan TcpListener, kami bisa mendengarkan koneksi TCP di alamat 127.0.0.1:7878. Di alamat, bagian sebelum titik dua adalah alamat IP yang mewakili komputer Anda (ini sama di setiap komputer dan tidak mewakili komputer penulis secara spesifik), dan 7878 adalah port. Kami memilih port ini karena dua alasan: HTTP biasanya tidak diterima di port ini, jadi server kami tidak akan konflik dengan web server lain yang mungkin Anda jalankan di mesin Anda, dan 7878 adalah rust yang diketik di telepon.

Fungsi bind dalam skenario ini bekerja seperti fungsi new karena ia akan mengembalikan instance TcpListener baru. Fungsi disebut bind karena, di jaringan, menghubungkan ke port untuk mendengarkan dikenal sebagai “binding ke port.”

Fungsi bind mengembalikan Result<T, E>, yang menunjukkan bahwa binding bisa gagal, misalnya, jika kita menjalankan dua instance program kita dan jadi ada dua program yang mendengarkan port yang sama. Karena kami menulis server dasar hanya untuk tujuan belajar, kami tidak akan khawatir menangani jenis error ini; sebagai gantinya, kami menggunakan unwrap untuk menghentikan program jika error terjadi.

Metode incoming pada TcpListener mengembalikan iterator yang memberi kami urutan stream (lebih spesifik, stream bertipe TcpStream). Satu stream mewakili koneksi terbuka antara client dan server. Connection adalah nama untuk proses permintaan dan respons penuh di mana client terhubung ke server, server menghasilkan respons, dan server menutup koneksi. Sebagai gantinya, kami akan membaca dari TcpStream untuk melihat apa yang dikirim client dan lalu menulis respons kami ke stream untuk mengirim data kembali ke client. Secara keseluruhan, loop for ini akan memproses setiap koneksi secara bergiliran dan menghasilkan serangkaian stream untuk kami tangani.

Saat ini, penanganan stream kami terdiri dari memanggil unwrap untuk menghentikan program jika stream punya error; jika tidak ada error, program mencetak pesan. Kami akan menambah fungsionalitas untuk kasus sukses di listing selanjutnya. Alasan kami mungkin menerima error dari metode incoming saat client terhubung ke server adalah bahwa kami benar-benar tidak mengiterasi koneksi. Sebagai gantinya, kami mengiterasi connection attempts. Koneksi mungkin tidak sukses karena sejumlah alasan, banyak di antaranya spesifik sistem operasi. Misalnya, banyak sistem operasi punya batas jumlah koneksi terbuka simultan yang bisa didukung; percobaan koneksi baru di luar angka itu akan menghasilkan error sampai beberapa koneksi terbuka ditutup.

Mari coba jalankan kode ini! Panggil cargo run di terminal lalu buka 127.0.0.1:7878 di browser web. Browser seharusnya menampilkan pesan error seperti “Connection reset” karena server saat ini tidak mengirim data kembali. Tapi saat Anda melihat terminal Anda, Anda seharusnya melihat beberapa pesan yang dicetak saat browser terhubung ke server!

Connection established!
Connection established!

Kadang Anda akan melihat beberapa pesan dicetak untuk satu permintaan browser; alasannya mungkin browser membuat permintaan untuk halaman serta permintaan untuk resource lain, seperti ikon favicon.ico yang muncul di tab browser.

Ini juga bisa jadi browser mencoba terhubung ke server beberapa kali karena server tidak merespons dengan data apa pun. Saat stream keluar dari scope dan di-drop di akhir loop, koneksi ditutup sebagai bagian dari implementasi drop. Browser kadang menangani koneksi tertutup dengan mencoba lagi, karena masalah mungkin bersifat sementara.

Browser juga kadang membuka beberapa koneksi ke server tanpa mengirim permintaan apa pun sehingga jika mereka nanti mengirim permintaan, permintaan itu bisa terjadi lebih cepat. Saat ini terjadi, server kami akan melihat setiap koneksi, tidak peduli apakah ada permintaan melalui koneksi itu. Banyak versi browser berbasis Chrome melakukan ini, misalnya; Anda bisa menonaktifkan optimisasi itu dengan menggunakan mode private browsing atau browser berbeda.

Faktor pentingnya adalah kami telah berhasil mendapatkan handle ke koneksi TCP!

Membaca Permintaan

Mari implementasikan fungsionalitas untuk membaca permintaan dari browser! Untuk memisahkan kepedulian pertama mendapatkan koneksi dan lalu melakukan tindakan dengan koneksi, kami akan memulai fungsi baru untuk memproses koneksi. Di fungsi handle_connection baru ini, kami akan membaca data dari stream TCP dan mencetaknya sehingga kami bisa melihat data yang dikirim dari browser. Ubah kode agar terlihat seperti Listing 21-2.

Kami memasukkan std::io::BufReader dan std::io::prelude ke scope untuk mendapatkan akses ke trait dan tipe yang memungkinkan kami membaca dari dan menulis ke stream. Di loop for di fungsi main, alih-alih mencetak pesan yang bilang kami membuat koneksi, kami sekarang memanggil fungsi handle_connection baru dan meneruskan stream kepadanya.

Di fungsi handle_connection, kami membuat instance BufReader baru yang membungkus referensi ke stream. BufReader menambah buffering dengan mengelola pemanggilan metode trait std::io::Read untuk kami.

Kami membuat variabel bernama http_request untuk mengumpulkan baris-baris permintaan yang dikirim browser ke server kami. Kami menunjukkan bahwa kami ingin mengumpulkan baris-baris ini ke vector dengan menambahkan anotasi tipe Vec<_>.

BufReader mengimplementasikan trait std::io::BufRead, yang menyediakan metode lines. Metode lines mengembalikan iterator Result<String, std::io::Error> dengan memecah stream data kapan pun ia melihat byte newline. Untuk mendapatkan setiap String, kami map dan unwrap setiap Result. Result mungkin error jika data bukan UTF-8 valid atau jika ada masalah membaca dari stream. Lagi lagi, program produksi seharusnya menangani error ini dengan lebih halus, tapi kami memilih untuk menghentikan program di kasus error untuk kesederhanaan.

Browser menandakan akhir permintaan HTTP dengan mengirim dua karakter newline berturut-turut, jadi untuk mendapatkan satu permintaan dari stream, kami mengambil baris sampai mendapat baris yang adalah string kosong. Setelah kami mengumpulkan baris-baris ke vector, kami mencetaknya menggunakan pretty debug formatting sehingga kami bisa melihat instruksi yang dikirim browser web ke server kami.

Melihat Lebih Dekat Permintaan HTTP

HTTP adalah protokol berbasis teks, dan permintaan mengambil format ini:

Method Request-URI HTTP-Version CRLF
headers CRLF
message-body

Baris pertama adalah request line yang menampung informasi tentang apa yang diminta client. Bagian pertama dari request line menunjukkan metode yang digunakan, seperti GET atau POST, yang mendeskripsikan bagaimana client membuat permintaan ini. Client kami menggunakan permintaan GET, yang berarti ia meminta informasi.

Bagian selanjutnya dari request line adalah /, yang menunjukkan uniform resource identifier (URI) yang diminta client: URI hampir, tapi tidak sama persis, dengan uniform resource locator (URL). Perbedaan antara URI dan URL tidak penting untuk tujuan kami di bab ini, tapi spesifikasi HTTP menggunakan istilah URI, jadi kami bisa hanya mengganti mental URL untuk URI di sini.

Bagian terakhir adalah versi HTTP yang digunakan client, dan lalu request line berakhir dalam urutan CRLF. (CRLF singkatan dari carriage return dan line feed, yang adalah istilah dari era mesin tik!) Urutan CRLF juga bisa ditulis sebagai \r\n, di mana \r adalah carriage return dan \n adalah line feed. Urutan CRLF memisahkan request line dari sisa data permintaan. Perhatikan bahwa saat CRLF dicetak, kami melihat awal baris baru bukannya \r\n.

Melihat data request line yang kami terima dari menjalankan program jauh ini, kami melihat bahwa GET adalah metode, / adalah request URI, dan HTTP/1.1 adalah versinya.

Setelah request line, sisa baris mulai dari Host: ke bawah adalah headers. Permintaan GET tidak punya body.

Coba buat permintaan dari browser berbeda atau minta alamat berbeda, seperti 127.0.0.1:7878/test, untuk melihat bagaimana data permintaan berubah.

Sekarang setelah kami tahu apa yang diminta browser, mari kirim kembali beberapa data!

Menulis Respons

Kami akan mengimplementasikan pengiriman data sebagai respons ke permintaan client. Respons memiliki format berikut:

HTTP-Version Status-Code Reason-Phrase CRLF
headers CRLF
message-body

Baris pertama adalah status line yang berisi versi HTTP yang digunakan di respons, kode status numerik yang merangkum hasil permintaan, dan reason phrase yang menyediakan deskripsi teks dari kode status. Setelah urutan CRLF adalah header apa pun, urutan CRLF lain, dan body respons.

Ini contoh respons yang menggunakan versi HTTP 1.1 dan punya kode status 200, reason phrase OK, tidak ada header, dan tidak ada body:

HTTP/1.1 200 OK\r\n\r\n

Kode status 200 adalah respons sukses standar. Teks ini adalah respons HTTP sukses kecil. Mari tulis ini ke stream sebagai respons kami ke permintaan sukses! Dari fungsi handle_connection, hapus println! yang mencetak data permintaan dan ganti dengan kode di Listing 21-3.

Baris baru pertama mendefinisikan variabel response yang menampung data pesan sukses. Lalu, kami memanggil as_bytes pada response kami untuk mengubah data string ke byte. Metode write_all pada stream mengambil &[u8] dan mengirim byte-byte itu langsung ke koneksi. Karena operasi write_all bisa gagal, kami menggunakan unwrap pada hasil error seperti sebelumnya. Lagi, di aplikasi nyata, Anda akan menambahkan penanganan error di sini.

Dengan perubahan ini, mari jalankan kode kami dan buat permintaan. Kami tidak lagi mencetak data ke terminal, jadi kami tidak akan melihat output selain output dari Cargo. Saat Anda memuat 127.0.0.1:7878 di browser web, Anda seharusnya mendapat halaman kosong alih-alih error. Anda baru saja menulis manual menerima permintaan HTTP dan mengirim respons!

Refactoring

Saat ini, blok if dan else punya banyak pengulangan: Keduanya membaca file dan menulis isi file ke stream. Satu-satunya perbedaan adalah status line dan nama file. Mari buat kode lebih ringkas dengan menarik perbedaan itu ke baris if dan else terpisah yang akan menetapkan nilai status line dan nama file ke variabel; kami kemudian bisa menggunakan variabel itu tanpa kondisi di kode untuk membaca file dan menulis respons. Listing 21-9 menunjukkan kode hasilnya setelah mengganti blok if dan else besar.

Sekarang blok if dan else hanya mengembalikan nilai yang sesuai untuk status line dan nama file dalam tuple; kami kemudian menggunakan destrukturisasi untuk menetapkan dua nilai ini ke status_line dan filename menggunakan pola di pernyataan let, seperti yang dibahas di Bab 19.

Kode yang duplikat sebelumnya sekarang di luar blok if dan else dan menggunakan variabel status_line dan filename. Ini membuat lebih mudah melihat perbedaan antara dua kasus, dan artinya kami hanya punya satu tempat untuk memperbarui kode jika kami ingin mengubah cara pembacaan file dan penulisan respons bekerja. Luar biasa! Kami sekarang punya web server sederhana dalam kira-kira 40 baris kode Rust yang merespons satu permintaan dengan halaman konten dan merespons semua permintaan lain dengan respons 404.

Saat ini, server kami berjalan di single thread, artinya ia hanya bisa melayani satu permintaan pada satu waktu. Mari periksa bagaimana itu bisa menjadi masalah dengan mensimulasikan beberapa permintaan lambat. Lalu, kami akan memperbaikinya sehingga server kami bisa menangani beberapa permintaan sekaligus.
